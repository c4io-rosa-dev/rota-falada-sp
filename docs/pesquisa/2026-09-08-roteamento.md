# Pesquisa: Motores de roteamento com perfil cadeirante (wheelchair) e incorporação de barreiras físicas reportadas por usuários — comparativo ORS, GraphHopper, Valhalla, OSRM, pgRouting, OSMnx/NetworkX + estimativa de declividade

## Resumo original
Entre os motores de roteamento livres, o OpenRouteService (ORS) é o único que oferece um perfil `wheelchair` pronto, documentado e disponível em API pública gratuita, com parâmetros diretamente ligados a acessibilidade (`maximum_incline`, `maximum_sloped_kerb`, `surface_type`, `smoothness_type`, `track_type`, `minimum_width`) e com `avoid_polygons`/`avoid_features: ["steps"]` aplicáveis em tempo de requisição — exatamente o gancho necessário para injetar as barreiras cadastradas pelos usuários sem reconstruir grafo. O plano gratuito dá 2.000 requisições/dia e 40/minuto para directions, o que é suficiente para um projeto acadêmico, e há limites de forma (polígono de evitar ≤ 200 km² e ≤ 20 km de extensão; rota com avoid areas ≤ 150 km) que não atrapalham rotas urbanas em São Paulo. O GraphHopper removeu o veículo `wheelchair` na versão 9.0 (abril/2024) e hoje exige reimplementá-lo como custom model; em compensação seu bloco `areas` (GeoJSON) dentro do `custom_model` enviado no POST /route permite penalização graduada (`multiply_by: 0.2`) e não apenas bloqueio duro — tecnicamente é o modelo mais elegante para "barreiras com severidade", mas exige auto-hospedagem em Java e escrever o perfil cadeirante do zero. O Valhalla tem `costing=pedestrian` com `type=wheelchair` (ajusta `max_distance`, `walking_speed`, `step_penalty`) mais `max_grade`, `exclude_polygons` e `exclude_locations` em tempo de requisição, sendo o segundo melhor candidato, porém é C++ e a construção de tiles é mais trabalhosa. O OSRM é o pior encaixe: o perfil Lua é aplicado só no pré-processamento, então qualquer mudança de regra ou barreira exige `osrm-extract` + `osrm-contract` novamente, sem avoid areas dinâmicas. pgRouting e OSMnx/NetworkX dão controle total sobre o custo por aresta (basta um UPDATE no PostGIS ou um atributo de peso no grafo) e são ótimos para um recorte pequeno, mas exigem construir todo o grafo de pedestres, penalidades e instruções de rota na mão. Para declividade, o caminho mais barato é o Open Topo Data público (SRTM 30 m, sem chave, 1.000 chamadas/dia, 100 pontos por chamada) ou o próprio ORS auto-hospedado com cache SRTM; para São Paulo especificamente existe o MDT LiDAR do GeoSampa (levantamentos 2017 e 2020, 10 pontos/m², PEC classe A), incomparavelmente mais preciso que SRTM para calcular inclinação de calçada, porém pesado e distribuído em quadrículas. A recomendação para orçamento zero e equipe pequena é: backend Python (FastAPI) consumindo a API pública do ORS com perfil `wheelchair`, gerando `avoid_polygons` a partir das barreiras validadas do banco filtradas por um corredor ao redor da rota inicial (padrão do exemplo oficial do ORS), com o plano B de subir o ORS em Docker com um recorte de São Paulo caso os limites da API pública apertem.

## Resumo corrigido pelo verificador (confiabilidade 7/10)
O relatório é sólido no essencial e a recomendação principal se sustenta após verificação: o OpenRouteService com perfil `wheelchair` é a escolha certa para o MVP, e praticamente todos os nomes de parâmetro, padrões e limites que ele cita do ORS conferem verbatim com a documentação oficial. Estão confirmados: as restrições `surface_type` (padrão cobblestone:flattened), `track_type` (grade1), `smoothness_type` (good), `maximum_sloped_kerb` (0.03 / 0.06 padrão / 0.1 / any), `maximum_incline` (3 / 6 padrão / 10 / 15 / any) e `minimum_width`; o `avoid_features` do perfil wheelchair aceitando exatamente 'steps' e 'ferries'; o `avoid_polygons` em GeoJSON Polygon/MultiPolygon em tempo de requisição; e as restrições de forma (6.000 km em geral, 300 km para wheelchair com restrições, 150 km com avoid areas, 200 km², 20 km de extensão, 50 waypoints). O comportamento de cota também está correto: 40 requisições de directions por janela deslizante de 60 segundos, HTTP 403 no estouro diário e HTTP 429 no minutário — mas o número de 2.000 requisições/dia NÃO aparece na fonte citada e fontes oficiais divergem entre ~2.000 e 2.500, então o backend deve ler os cabeçalhos `x-ratelimit-remaining` e `x-ratelimit-reset` em vez de assumir um valor fixo. A tese de exclusividade cai: o Valhalla também tem modo cadeirante pronto e documentado (`costing=pedestrian`, `type=wheelchair`) e existe instância pública gratuita da FOSSGIS com o planeta inteiro em valhalla1.openstreetmap.de, sob política de uso justo de 1 requisição por usuário por segundo — o correto é dizer que o ORS é o mais parametrizável para acessibilidade, não o único. Ainda no Valhalla, dois detalhes do relatório estão errados: `walkway_factor` tem padrão 1.0 (e não 0.9), e `max_grade` é lido pelo parser mas a verificação está desativada no código-fonte com o comentário 'currently disabled bcs of noisy data', além de não constar da tabela oficial de opções — ou seja, não serve como teto de inclinação; vale registrar também que o modo wheelchair do Valhalla impõe max_distance de apenas 10 km, contra 100 km a pé. Sobre o GraphHopper, tudo confere: a remoção do veículo wheelchair na versão 9.0 (23/04/2024) está literal no CHANGELOG, o bloco `areas` é FeatureCollection GeoJSON com geometrias Polygon, referências prefixadas por `in_`, bloqueio por multiply_by 0 e `ch.disable: true` no POST; o único ajuste é que o import do planeta com MMAP cai de ~60 GB para 31 GB de RAM mas sobe de ~3 horas para ~3 dias, o que é um custo muito maior do que o relatório sugere. A conclusão sobre o OSRM está correta e até reforçada: perfis Lua só valem no pré-processamento, e mesmo o recurso `excludable` exige declarar antes quais classes poderão ser excluídas. Na parte de dados de São Paulo há erros a corrigir: o MDT LiDAR de 10 pontos/m² com PEC-PCD classe A e resolução de 0,50 m é o levantamento de 2020 (o de 2017 tem densidade nominal média de 8 pontos/m²), o formato é LAZ em 5.362 quadrículas, e a URL de metadado citada no relatório aponta para a camada de articulação (índice de quadrículas) do MDT/MDS 2017, não para o modelo de terreno. Os limites de elevação estão certos: Open Topo Data com 100 localizações por requisição, 1 chamada por segundo e 1.000 por dia, sem chave; Open-Elevation com 1.000 requisições/mês no gratuito e €50/mês no plano com resolução maior. Uma correção prática importante na stack: a openrouteservice-py, apresentada como argumento decisivo a favor de Python, está sem release desde a versão 2.3.3 de fevereiro de 2021 e testada só até Python 3.9 — Python continua sendo a escolha certa pelo ecossistema (shapely, pyproj, geopandas, rasterio), mas o cliente deve ser routingpy ou uma chamada REST direta com httpx. A atribuição exigida também está errada no relatório: o texto correto é '© openrouteservice.org by HeiGIT | Map data © OpenStreetMap contributors', e os resultados da API são licenciados sob CC-BY 4.0. Por fim, o relatório provavelmente reinventa trabalho ao propor consultas ponto a ponto de elevação: com `elevation=true` e `extra_info=steepness|surface|waytype`, a própria resposta do ORS já traz declividade e superfície por segmento, sem chamada externa. As lacunas mais sérias são de escopo: nada sobre a SPTrans e roteamento multimodal (que exigiria OpenTripPlanner com GTFS e os campos wheelchair_accessible/wheelchair_boarding), nada sobre a NBR 9050 para justificar os valores de inclinação e largura escolhidos, nada sobre LGPD para dados de localização de pessoas com deficiência, e nada sobre a acessibilidade WCAG/eMAG da própria interface — que é o critério central da disciplina e o ponto onde um mapa interativo mais falha diante de um leitor de tela.

## Afirmações refutadas
- **O OpenRouteService (ORS) é o único motor de roteamento livre que oferece um perfil `wheelchair` pronto, documentado e disponível em API pública gratuita.**
  - Motivo: Falso como exclusividade. O Valhalla também traz um modo cadeirante pronto e documentado (`costing=pedestrian` + `costing_options.pedestrian.type="wheelchair"`), e existe instância pública gratuita com o planeta inteiro mantida pela FOSSGIS e.V. em https://valhalla1.openstreetmap.de (o app demo fica em https://valhalla.openstreetmap.de). Ou seja, há pelo menos dois motores com perfil cadeirante pronto e API pública grátis. O relatório reconhece o `type=wheelchair` do Valhalla em outro ponto, o que torna a afirmação de exclusividade internamente contraditória.
  - Correção: Corrigir para: 'o ORS é o motor com o perfil wheelchair mais parametrizável e melhor documentado, e o único cuja API pública gratuita expõe restrições de acessibilidade granulares (maximum_incline, maximum_sloped_kerb, minimum_width, smoothness_type, surface_type). O Valhalla também tem modo wheelchair pronto e instância pública gratuita da FOSSGIS, porém com política de uso justo (1 requisição/usuário/segundo, header X-Client-Id recomendado para apps) e sem as restrições finas do ORS.'
  - Fonte: https://valhalla.github.io/valhalla/api/route/api-reference/ ; https://github.com/valhalla/valhalla/discussions/3373 ; https://valhalla.openstreetmap.de/
- **O Valhalla expõe `walkway_factor` com padrão 0.9.**
  - Motivo: Refutado por duas fontes independentes. A tabela oficial de opções de pedestrian costing e o código-fonte concordam que o padrão é 1.0 (valor neutro): em src/sif/pedestriancost.cc, `kDefaultWalkwayFactor = 1.0f` e `kDefaultSideWalkFactor = 1.0f`.
  - Correção: walkway_factor e sidewalk_factor têm padrão 1.0 (neutro), não 0.9. Para preferir calçadas/passeios é preciso baixar o fator explicitamente (ex.: sidewalk_factor 0.7). Os padrões corretos confirmados: alley_factor 2.0, driveway_factor 5.0, walking_speed 5.1 km/h (modo foot), max_distance 100 km (modo foot).
  - Fonte: https://raw.githubusercontent.com/valhalla/valhalla/master/src/sif/pedestriancost.cc ; https://valhalla.github.io/valhalla/api/route/api-reference/
- **O Valhalla expõe `max_grade` no costing pedestrian, 'relevante para inclinação', como parâmetro utilizável para restringir declividade em rotas de cadeirante.**
  - Motivo: Enganoso a ponto de ser refutado na prática. O parâmetro é lido pelo parser (`"max_grade"` → `max_grade_` em pedestriancost.cc), mas a verificação que efetivamente filtraria arestas está DESATIVADA no código, com o comentário explícito '(currently disabled bcs of noisy data)'. Além disso, `max_grade` não aparece na tabela de opções de pedestrian costing da referência oficial da API. Enviar max_grade=6 é aceito e não produz o efeito esperado.
  - Correção: Não contar com `max_grade` do Valhalla como controle de inclinação. O Valhalla trata relevo via `use_hills` e fatores de velocidade por grade (kGradeBasedSpeedFactor), que penalizam mas não impõem teto. Se o requisito for teto duro de inclinação (ex.: 'nada acima de 8,33%, limite da NBR 9050'), o ORS com `maximum_incline` é hoje a única opção pronta entre os motores avaliados.
  - Fonte: https://raw.githubusercontent.com/valhalla/valhalla/master/src/sif/pedestriancost.cc ; https://raw.githubusercontent.com/valhalla/valhalla/master/docs/docs/api/route/api-reference.md
- **O GeoSampa disponibiliza o MDT LiDAR de São Paulo com densidade de 10 pontos/m², com levantamentos de 2017 e 2020, PEC classe A, distribuído em DXF/LAZ; fonte: metadados .../records/03944df3-cd3c-4ea1-bbe8-44732d6f8be4.**
  - Motivo: Três erros. (1) A densidade de 10 pontos/m² e o PEC-PCD classe A referem-se ao levantamento de 2020; o levantamento de 2017 tem 'densidade nominal média de 8 ptos/m2' segundo o próprio metadado. (2) A URL citada NÃO é o MDT: é a camada de articulação (índice de quadrículas) do MDT/MDS 2017, um vetor de limites de quadrículas distribuído como Postgis-OGC/WFS/WMS — não o modelo de terreno. O registro correto da nuvem de pontos MDT 2020 é .../records/b9b1b6d2-eb59-49fc-8ba7-66e75eb552a6. (3) O formato de distribuição do MDT é LAZ (LAS comprimido), com resolução espacial de 0,50 m e radiométrica de 32 bits; DXF não é o formato do MDT (é o formato do mapeamento topográfico antigo do município).
  - Correção: Usar: 'MDT derivado de LiDAR, levantamento de 2020, densidade média de 10 pontos/m², precisão da ordem de 10 cm, PEC-PCD classe A, resolução espacial de 0,50 m, distribuído em LAZ em 5.362 quadrículas identificadas por um ID de 7 dígitos (camada Articulação de Imagens > MDT/MDS 2020 no portal). O levantamento anterior, de fev-jun/2017, tem densidade nominal média de 8 pontos/m².'
  - Fonte: https://metadados.geosampa.prefeitura.sp.gov.br/geonetwork/srv/api/records/03944df3-cd3c-4ea1-bbe8-44732d6f8be4 ; https://metadados.geosampa.prefeitura.sp.gov.br/geonetwork/srv/api/records/b9b1b6d2-eb59-49fc-8ba7-66e75eb552a6 ; https://github.com/geoinfo-smdu/usando-MDT

  - Motivo: O fato de ser oficial é verdadeiro, mas o relatório omite que a biblioteca está efetivamente parada: a última versão no PyPI é a 2.3.3, publicada em 2 de fevereiro de 2021 — mais de cinco anos sem release —, e a matriz de testes declarada vai só até CPython 3.9. ## Lacunas apontadas
- A proposta oficial do projeto cita a SPTrans Olho Vivo (ônibus acessíveis em tempo real) e o relatório simplesmente não trata de multimodal: nenhum dos motores comparados resolve 'ir de cadeira de rodas de A a B usando ônibus acessível'. Falta avaliar o OpenTripPlanner (OTP), que consome GTFS + OSM e é o motor natural para roteamento multimodal acessível (o GTFS tem o campo wheelchair_accessible em trips e wheelchair_boarding em stops, exatamente o dado que a SPTrans publica). Sem isso o relatório responde só metade da proposta.
- Não menciona os cabeçalhos `x-ratelimit-remaining` e `x-ratelimit-reset`, documentados na própria FAQ do ORS que o relatório cita, para checar a cota programaticamente. Essa é justamente a dica de 'monitorar chaves de API' do enunciado do projeto, e é a forma correta de resolver a divergência de fontes sobre 2.000 vs 2.500 requisições/dia.
- Não registra que, desde o início de 2025, a gestão de usuários do ORS migrou para account.heigit.org e as chaves novas são JWT — o que quebra tutoriais e exemplos antigos (inclusive muita coisa que a equipe vai achar no Google) e afeta a forma de guardar/rotacionar a chave no backend.
- Não avalia o ORS `extra_info` (steepness, surface, waytype, suitability, traildifficulty) nem os campos ascent/descent da resposta. Isso é uma lacuna cara: com elevation=true e extra_info=steepness a própria resposta de rota já devolve a classificação de declividade por segmento, o que pode eliminar totalmente a necessidade de chamar Open Topo Data ponto a ponto — a arquitetura recomendada no relatório é mais complicada do que precisa.
- Não menciona o `max_distance` padrão de 10 km do Valhalla no modo wheelchair (kMaxDistanceWheelchair = 10000, contra 100 km no modo foot), nem a velocidade padrão de 4,0 km/h e o step_penalty de 600 s. É um teto silencioso que faria rotas longas falharem sem explicação óbvia.
- Não cita nenhuma referência normativa brasileira de acessibilidade. Para justificar os valores escolhidos de maximum_incline e minimum_width na banca, o parâmetro certo é a ABNT NBR 9050 (inclinação de rampas, largura mínima de faixa livre de calçada, desnível máximo de guia rebaixada), não um número escolhido por intuição. Isso conecta diretamente com os campos maximum_incline / minimum_width / maximum_sloped_kerb do ORS.
- Não trata da acessibilidade do próprio produto, que é o critério central da disciplina: um mapa é o componente mais hostil que existe para leitor de tela. Faltou discutir como entregar a rota em alternativa textual navegável (lista de instruções com landmarks, ARIA live region para atualização de rota, foco gerenciado, contraste, operação só por teclado) e as APIs nativas de Speech Synthesis/Recognition sugeridas no enunciado. Roteamento perfeito com interface inacessível reprova no que a matéria avalia.
- Não trata de tiles de mapa no frontend. O motor de rota é grátis, mas o mapa também precisa ser desenhado: o tile server padrão do OpenStreetMap tem política de uso que desencoraja aplicações, e a escolha entre MapLibre/Leaflet com um provedor gratuito (e seus limites) é uma decisão de custo zero real que ficou de fora.
- Não menciona LGPD. O sistema registra localização de pessoas com deficiência e mobilidade reduzida — condição de saúde é dado pessoal sensível. Coletar posição de quem reporta barreira, ou histórico de rotas, exige base legal e minimização; isso deveria estar nos riscos e rende pontos no relatório acadêmico.
- Não discute persistência nem esquema do banco de barreiras (geometria ponto vs. segmento, severidade, confirmações, expiração, moderação), apesar de a lógica de negócio proposta depender inteiramente disso. Também não aborda o problema de fazer buffer em metros: cita EPSG:31983 na recomendação, mas não trata do caso de barreiras próximas ao limite de fuso.
- Não avalia hospedagem concretamente. Diz que free tiers não comportam 4-8 GB, mas não propõe alternativa viável para o dia da apresentação (ex.: rodar o ORS só como plano B local com túnel, ou usar a instância pública da FOSSGIS para Valhalla como fallback de disponibilidade). O 'plano B' fica sem plano C.
- Divergência não notada entre fontes do próprio ORS: a página de restrições da API pública anuncia 150 km para rotas com avoid areas, enquanto o ors-config.yml distribuído traz maximum_distance_avoid_areas: 100000 (100 km). Ao auto-hospedar, o teto padrão é MENOR que o da API pública — o oposto do que o relatório sugere ao dizer que auto-hospedar afrouxa todos os tetos.
- Não menciona alternativas ao osm2pgrouting (que está sem release desde jun/2021 e carrega tudo em memória), como osm2po ou a construção de topologia a partir de osm2pgsql — relevante se a equipe realmente for usar pgRouting para as consultas espaciais recomendadas.

## Fatos levantados
- [alta] O openrouteservice possui um perfil `wheelchair` de primeira classe na API pública, com restrições específicas em `options.profile_params.restrictions`: surface_type (padrão "cobblestone:flattened"), track_type (padrão "grade1"), smoothness_type (padrão "good"), maximum_sloped_kerb (0.03, 0.06, 0.1 ou "any"), maximum_incline (3, 6, 10, 15 ou "any", padrão 6) e minimum_width em metros. (fonte: https://giscience.github.io/openrouteservice/api-reference/endpoints/directions/routing-options)
- [alta] No ORS, `avoid_features` aceita "steps" e "ferries" para o perfil wheelchair — ou seja, é possível eliminar escadas do grafo com um único parâmetro, sem nenhum pré-processamento. (fonte: https://giscience.github.io/openrouteservice/api-reference/endpoints/directions/routing-options)
- [alta] O ORS aceita `avoid_polygons` como GeoJSON Polygon ou MultiPolygon (RFC 7946) em tempo de requisição, permitindo injetar barreiras cadastradas por usuários sem reconstruir o grafo. É um bloqueio duro (a via é removida), não uma penalidade graduada. (fonte: https://giscience.github.io/openrouteservice/api-reference/endpoints/directions/routing-options)
- [alta] O limite padrão do plano gratuito do ORS para directions é 2.000 requisições por dia e 40 requisições por janela deslizante de 60 segundos. Estourar o limite diário devolve HTTP 403; estourar o limite por minuto devolve HTTP 429. A cota restante aparece no dashboard do desenvolvedor. (fonte: https://giscience.github.io/openrouteservice/frequently-asked-questions)
- [alta] Restrições de forma do ORS relevantes para o projeto: distância máxima 6.000 km em geral, mas 150 km quando se usam avoid areas e 300 km para wheelchair com restrições de perfil; área máxima de polígono a evitar 200 km²; extensão máxima do polígono (altura ou largura) 20 km; máximo de 50 waypoints por rota. (fonte: https://openrouteservice.org/restrictions/)
- [alta] O exemplo oficial do ORS de "avoid obstacles while routing" faz exatamente o fluxo que o projeto precisa: cria buffers de 10 m ao redor de pontos de obstáculo (via pyproj WGS84↔UTM + shapely), pede a rota inicial, filtra apenas os obstáculos que interceptam essa rota (para não estourar o tamanho da requisição) e refaz a rota com `avoid_polygons`. (fonte: https://openrouteservice.org/example-avoid-obstacles-while-routing/)
- [alta] Auto-hospedar o ORS é simples: baixar o docker-compose.yml da última release e rodar `docker compose up -d`. O perfil wheelchair é ativado por variável de ambiente (`ors.engine.profiles.wheelchair.enabled: true`), o .osm.pbf próprio vai em `ors-docker/files/` apontado por `ors.engine.profile_default.build.source_file`, e a memória da JVM é controlada por XMS/XMX. (fonte: https://giscience.github.io/openrouteservice/run-instance/running-with-docker)
- [alta] Requisitos de RAM do ORS por tamanho de extrato OSM (documentação oficial): Baden-Württemberg (PBF de 450 MB) → 2-4 GB; Alemanha (PBF de 3 GB) → ~8 GB; planeta (~50 GB) → 100-105 GB. Perfis de pedestre e bicicleta consomem mais memória que os de carro, e mais RAM acelera o build por reduzir garbage collection. (fonte: https://giscience.github.io/openrouteservice/run-instance/system-requirements)
- [media] O extrato Geofabrik `brazil/sudeste-latest.osm.pbf` tem 817 MB (Brasil inteiro: 1,9 GB). Por comparação com Baden-Württemberg (450 MB → 2-4 GB de RAM), um recorte só do município de São Paulo (bem menor que o Sudeste inteiro, gerado com osmium extract por bounding box) deve caber confortavelmente em 4-8 GB de RAM num notebook comum. (fonte: https://download.geofabrik.de/south-america/brazil.html)
- [alta] O GraphHopper removeu o veículo `wheelchair` e seus parsers na versão 9.0 (abril/2024), sem substituto completo — a orientação oficial é reimplementá-lo como custom model, porque a versão antiga não estava pronta para produção. (fonte: https://github.com/graphhopper/graphhopper/blob/master/CHANGELOG.md)
- [alta] Custom models do GraphHopper podem ser enviados em tempo real no corpo do POST /route (com `ch.disable=true`), e incluem um bloco `areas` com FeatureCollection GeoJSON: condições como `if: "in_barreira_123"` com `multiply_by: 0` bloqueiam a região e valores entre 0 e 1 aplicam penalidade graduada. Isso permite modelar severidade de barreira, algo que o `avoid_polygons` do ORS não faz. (fonte: https://github.com/graphhopper/graphhopper/blob/master/docs/core/custom-models.md)
- [alta] Encoded values do GraphHopper úteis para acessibilidade: foot_access, road_class (FOOTWAY, PATH, etc.), surface (PAVED, GRAVEL, DIRT, SAND), road_environment, hike_rating e — importante para declividade — average_slope e max_slope. (fonte: https://github.com/graphhopper/graphhopper/blob/master/docs/core/custom-models.md)
- [alta] O Valhalla tem `costing=pedestrian` com atributo `type` que aceita `foot` (padrão) ou `wheelchair`; com wheelchair ele altera os defaults de max_distance, walking_speed e step_penalty. Também expõe max_grade (relevante para inclinação), sidewalk_factor, walkway_factor (padrão 0.9), alley_factor (2.0), driveway_factor (5.0), step_penalty e max_hiking_difficulty. (fonte: https://valhalla.github.io/valhalla/api/route/api-reference/)
- [alta] O Valhalla aceita `exclude_polygons` (anéis poligonais — vias que os interceptam são evitadas) e `exclude_locations` (pontos mapeados para a via mais próxima, que é excluída do cálculo) em tempo de requisição. `exclude_locations` é especialmente conveniente para barreiras pontuais como um degrau ou um poste no meio da calçada. (fonte: https://valhalla.github.io/valhalla/api/route/api-reference/)
- [alta] No OSRM os perfis Lua são aplicados no pré-processamento, não em tempo de consulta: depois de alterar um perfil é obrigatório rodar novamente osrm-extract, osrm-contract e recarregar os dados. Não há avoid areas dinâmicas (só avoid de tolls/motorways/ferries em alguns perfis). (fonte: https://github.com/Project-OSRM/osrm-backend/blob/master/docs/profiles.md)
- [media] Existem perfis Lua comunitários de cadeira de rodas para OSRM (species/osrm-wheelchair-profiles, com variantes como wheelchair-normal.lua), mas eles herdam a limitação de exigir reprocessamento a cada mudança. (fonte: https://github.com/species/osrm-wheelchair-profiles/blob/master/wheelchair-normal.lua)
- [alta] pgRouting + PostGIS permite custo totalmente dinâmico: o osm2pgrouting importa o OSM criando tabelas de types/classes que servem de base para funções de custo sofisticadas, e o custo de cada aresta é apenas uma coluna SQL — uma barreira reportada vira um UPDATE na coluna cost/reverse_cost, aplicado na próxima consulta sem rebuild. (fonte: https://pgrouting.org/docs/tools/osm2pgrouting.html)
- [alta] OSMnx (Python) baixa a rede via Overpass e a modela como MultiDiGraph do NetworkX, com atributos por aresta que podem ser usados como weight customizado em algoritmos de caminho mínimo. É a rota de menor atrito para prototipar penalização dinâmica em Python puro, mas o grafo fica em memória e não há instruções turn-by-turn prontas. (fonte: https://osmnx.readthedocs.io/)
- [alta] O Open Topo Data oferece API pública gratuita sem chave com limites de 100 localizações por requisição, 1 chamada por segundo e 1.000 chamadas por dia, com datasets SRTM 30 m e 90 m, ASTER, NASADEM, Mapzen e outros; pode ser auto-hospedado com Docker (git clone + make build + make run, servidor em localhost:5000). (fonte: https://www.opentopodata.org/)
- [media] O Open-Elevation público anuncia apenas cerca de 1.000 requisições/mês no plano gratuito, com maior resolução apenas nos planos pagos (a partir de ~€50/mês), mas o projeto é open source e auto-hospedável. (fonte: https://open-elevation.com/)
- [alta] O GeoSampa disponibiliza o MDT (Modelo Digital de Terreno) de São Paulo gerado por LiDAR com densidade de 10 pontos/m², com levantamentos de 2017 e 2020, qualificado com PEC classe A, distribuído por quadrículas para download (DXF/LAZ). É a fonte de elevação de maior precisão disponível gratuitamente para o município. (fonte: https://metadados.geosampa.prefeitura.sp.gov.br/geonetwork/srv/api/records/03944df3-cd3c-4ea1-bbe8-44732d6f8be4)
- [media] A configuração padrão do ORS usa `elevation.provider: multi` com cache local e acesso MMAP; há um problema conhecido de que a URL do provedor CGIAR ficou offline, o que faz o ORS lançar erro se CGIAR ou MULTI estiverem configurados — atenção ao auto-hospedar com elevação ligada. (fonte: https://github.com/GIScience/openrouteservice/issues/1866)
- [alta] Os limites de configuração do ORS auto-hospedado são ajustáveis: maximum_avoid_polygon_area (padrão 200000000 m² = 200 km²), maximum_avoid_polygon_extent (20000 m), maximum_distance (100000 m) e maximum_waypoints (50) — ou seja, ao auto-hospedar você pode afrouxar todos os tetos que incomodam na API pública. (fonte: https://github.com/GIScience/openrouteservice/blob/main/ors-config.yml)
- [media] O ORS mantém bibliotecas cliente oficiais para Python (openrouteservice-py), JavaScript (openrouteservice-js), R e um plugin QGIS. Não há cliente oficial para C#/.NET — nesse caso seria consumo REST direto com HttpClient. (fonte: https://github.com/GIScience/openrouteservice-py)
- [alta] O perfil wheelchair do ORS depende das tags OSM incline, surface, smoothness, width, kerb e das tags de calçada (sidewalk:*), aplicando filtragem dinâmica: elementos são incluídos ou excluídos do grafo conforme as preferências do perfil. A grande limitação reconhecida é a escassez de dados de calçada no OSM — justamente a lacuna que o cadastro colaborativo do projeto pretende preencher. (fonte: https://giscienceblog.uni-heidelberg.de/2015/04/14/option-for-wheelchair-routing-now-available-within-openrouteservice/)
- [alta] O GraphHopper é escrito em Java e pode ser embutido como biblioteca dentro de uma aplicação Java (sem camada HTTP). Construir o grafo do planeta exige ~60 GB de RAM e ~3 h; um extrato municipal exige ordens de grandeza menos, e há a opção graph.dataaccess.default_type=MMAP para reduzir uso de heap ao custo de velocidade de import. (fonte: https://github.com/graphhopper/graphhopper/blob/master/docs/core/deploy.md)
- [media] Existem bindings Python de alto nível para o Valhalla (pyvalhalla), que embutem os executáveis C++ (ex.: python -m valhalla valhalla_build_tiles), e o Valhalla usa tiles hierárquicos com memory-mapping, o que dá pegada de memória pequena e compartilhamento entre workers — bom para hospedagem gratuita com pouca RAM. (fonte: https://valhalla.github.io/valhalla/bindings/python/)

## Endpoints / recursos
- **ORS Directions — perfil wheelchair (API pública)** — POST https://api.openrouteservice.org/v2/directions/wheelchair/geojson (header Authorization: <API_KEY>)
  - Retorna: Rota em GeoJSON/JSON/GPX com geometria, distância, duração e instruções passo a passo, respeitando as restrições de acessibilidade e os polígonos a evitar.
  - Exemplo: `{"coordinates":[[-46.6333,-23.5505],[-46.6560,-23.5630]],"options":{"avoid_features":["steps"],"avoid_polygons":{"type":"MultiPolygon","coordinates":[[[[-46.641,-23.556],[-46.640,-23.556],[-46.640,-23.555],[-46.641,-23.555],[-46.641,-23.556]]]]},"profile_params":{"restrictions":{"maximum_incline":6,"maximum_sloped_kerb":0.06,"minimum_width":0.9,"surface_type":"cobblestone:flattened","smoothness_type":"good"}}},"elevation":true,"instructions":true}`
- **ORS Isochrones (áreas alcançáveis a partir de um ponto)** — POST https://api.openrouteservice.org/v2/isochrones/wheelchair
  - Retorna: Polígonos de alcance em tempo ou distância — útil para a tela "o que consigo alcançar em 15 min de cadeira de rodas a partir daqui".
  - Exemplo: `{"locations":[[-46.6333,-23.5505]],"range":[600,900],"range_type":"time"}`
- **openrouteservice-py (cliente oficial Python)** — pip install openrouteservice; client = openrouteservice.Client(key=...); client.directions(coords, profile='wheelchair', options={...})
  - Retorna: Dicionário Python com a resposta da API; integra bem com shapely/geopandas para montar os polígonos de barreira.
  - Exemplo: `https://openrouteservice-py.readthedocs.io/en/latest/`
- **ORS auto-hospedado via Docker** — wget docker-compose.yml da última release + docker compose up -d; PBF próprio em ors-docker/files/; env ors.engine.profiles.wheelchair.enabled: true; XMS/XMX para a JVM
  - Retorna: Instância local com a mesma API REST, sem limite de requisições e com maximum_avoid_polygon_area/extent/maximum_distance ajustáveis no ors-config.yml.
  - Exemplo: `https://giscience.github.io/openrouteservice/run-instance/running-with-docker`
- **GraphHopper POST /route com custom_model e areas** — POST /route com {"profile":"foot_custom","ch.disable":true,"custom_model":{"priority":[{"if":"in_barreira_42","multiply_by":"0.05"}],"areas":{...FeatureCollection...}}}
  - Retorna: Rota com penalidade graduada por área — permite modelar severidade da barreira (calçada ruim = 0.3, escada = 0) em vez de bloqueio binário.
  - Exemplo: `https://github.com/graphhopper/graphhopper/blob/master/docs/core/custom-models.md`
- **Valhalla /route com costing=pedestrian type=wheelchair** — POST /route com {"costing":"pedestrian","costing_options":{"pedestrian":{"type":"wheelchair","max_grade":6,"step_penalty":600,"sidewalk_factor":0.7}},"exclude_polygons":[...],"exclude_locations":[...]}
  - Retorna: Rota com narrativa turn-by-turn; exclude_polygons/exclude_locations aplicam as barreiras em tempo de requisição.
  - Exemplo: `https://valhalla.github.io/valhalla/api/route/api-reference/`
- **Open Topo Data (elevação, sem chave)** — GET https://api.opentopodata.org/v1/srtm30m?locations=-23.5505,-46.6333|-23.5630,-46.6560
  - Retorna: Elevação em metros por ponto; com dois pontos consecutivos de um segmento calcula-se a declividade = Δh/Δd. Auto-hospedável em Docker para remover o limite.
  - Exemplo: `1.000 chamadas/dia, 100 pontos por chamada, 1 chamada/s — https://www.opentopodata.org/`
- **GeoSampa — MDT LiDAR de São Paulo** — Portal GeoSampa > Pesquisar > aba "Download Imagens/MDC" > tipo "MDT" > selecionar quadrículas no mapa
  - Retorna: Modelo Digital de Terreno por quadrícula (LiDAR 10 pontos/m², levantamentos 2017 e 2020, PEC classe A) — precisão de calçada, muito superior ao SRTM de 30 m para estimar rampas.
  - Exemplo: `https://geosampa.prefeitura.sp.gov.br/ ; tutoriais em https://github.com/geoinfo-smdu/usando-MDT e https://github.com/cem-usp/mdt-sampa`
- **Geofabrik — extrato OSM do Sudeste** — https://download.geofabrik.de/south-america/brazil/sudeste-latest.osm.pbf (817 MB), recortado com `osmium extract -b bbox`
  - Retorna: Arquivo .osm.pbf usado para construir o grafo de qualquer motor auto-hospedado (ORS, GraphHopper, Valhalla, OSRM, pgRouting).
  - Exemplo: `osmium extract -b -46.83,-24.01,-46.36,-23.35 sudeste-latest.osm.pbf -o sao-paulo.osm.pbf`
- **osm2pgrouting / pgRouting** — osm2pgrouting -f sao-paulo.osm -c mapconfig_for_pedestrian.xml -d db ...; depois SELECT * FROM pgr_dijkstra('SELECT id, source, target, cost, reverse_cost FROM ways', src, tgt)
  - Retorna: Caminho mínimo com custo definido em SQL — barreiras entram como UPDATE na coluna cost, sem rebuild de grafo.
  - Exemplo: `https://pgrouting.org/docs/tools/osm2pgrouting.html`

## Limites e custos
CUSTO DIRETO: zero em todos os caminhos avaliados. Nenhum dos motores (ORS, GraphHopper, Valhalla, OSRM, pgRouting, OSMnx) cobra licença — todos são open source. O que existe são limites de cota nas APIs públicas.

ORS API pública (plano gratuito, exige cadastro em account.heigit.org e chave enviada no header Authorization):
- Directions: 2.000 requisições/dia e 40 requisições por janela deslizante de 60 s. Estouro diário = HTTP 403; estouro por minuto = HTTP 429.
- Restrições de forma: distância máx. 6.000 km em geral, 150 km quando se usa avoid areas, 300 km para wheelchair com restrições de perfil; polígono a evitar ≤ 200 km² e ≤ 20 km de extensão; ≤ 50 waypoints. Nenhuma delas atrapalha rotas urbanas em São Paulo (uma rota a pé raramente passa de 10 km).
- Consequência prática: 2.000 rotas/dia dividido entre todos os usuários da banca e da demo. Cada tela que recalcula rota a cada arrastar de marcador consome cota rápido — é obrigatório fazer debounce no frontend e cache no backend (chave = origem+destino arredondados + hash do conjunto de barreiras).
- Uma limitação relevante para o projeto: `avoid_polygons` só faz bloqueio duro; não há como dizer "essa calçada é ruim mas passável". A granularidade de severidade precisa ser resolvida na sua camada (ex.: só virar polígono quem tiver severidade alta e N confirmações).
- Requisições GET têm limite de tamanho de URL; com muitos polígonos é obrigatório usar POST.

ORS auto-hospedado: gratuito e sem cota. Custo é de infraestrutura e tempo. RAM pela documentação oficial: PBF de 450 MB → 2-4 GB; PBF de 3 GB → ~8 GB. Um recorte só do município de São Paulo (via osmium extract do sudeste-latest.osm.pbf de 817 MB) deve ficar na casa de 4-8 GB de RAM — roda em notebook, não roda em free tier de PaaS (Render/Fly.io free ficam abaixo disso). Ao auto-hospedar, todos os tetos (maximum_avoid_polygon_area, maximum_distance, maximum_waypoints) são ajustáveis no ors-config.yml.

Elevação:
- Open Topo Data público: grátis, sem chave, 1.000 chamadas/dia, 1 chamada/s, 100 pontos por chamada (= até 100.000 pontos/dia). Auto-hospedável em Docker sem limite.
- Open-Elevation público: bem mais apertado (~1.000 requisições/mês anunciadas); planos pagos a partir de ~€50/mês. Auto-hospedável.
- Mapbox Terrain-RGB: free tier generoso (dezenas de milhares de carregamentos/mês) mas exige conta com cartão e conta como serviço proprietário — risco de custo inesperado; evitar em projeto com orçamento zero rígido.
- GeoSampa MDT: gratuito e sem cadastro, mas é download em lote de quadrículas LiDAR (gigabytes), processado offline uma vez — custo é de disco e tempo de processamento, não de API.
- SRTM 30 m tem erro vertical de vários metros e resolução horizontal maior que a largura de uma calçada: serve para dizer "essa rua sobe o morro", não para dizer "essa rampa tem 6%".

TERMOS DE USO: ORS/HeiGIT exige atribuição ("powered by openrouteservice / HeiGIT") e o uso é sob os termos em openrouteservice.org/terms-of-service. Dados OSM sob ODbL — exige atribuição "© OpenStreetMap contributors" e, atenção, dados derivados de OSM redistribuídos podem ser considerados database derivada (relevante se vocês publicarem o dataset de barreiras junto). GeoSampa tem termos próprios da Prefeitura de São Paulo — verificar antes de redistribuir os arquivos.

## Riscos
- Dependência de dado que não existe: o perfil wheelchair do ORS só é bom onde as tags OSM (incline, surface, smoothness, width, kerb, sidewalk:*) estão preenchidas. Em grande parte de São Paulo elas não estão, e o ORS pode devolver uma rota 'acessível' que na prática atravessa uma calçada destruída. Isso não é bug do motor — é lacuna de dado, e é exatamente o que o cadastro colaborativo do projeto existe para cobrir. Nunca prometa garantia de acessibilidade na UI.
- Filtragem agressiva demais = 'rota não encontrada'. Com maximum_incline=3 e smoothness_type=excellent, o ORS remove tantas vias do grafo que muitas rotas ficam impossíveis. Sem um fallback (relaxar restrições progressivamente e avisar o usuário), a demo quebra na frente da banca.
- avoid_polygons é bloqueio binário: se o usuário cadastrar barreiras demais numa região, o roteador pode não achar caminho nenhum, ou dar uma volta absurda. Precisa de limite no número de polígonos enviados (filtrar por corredor ao redor da rota, como faz o exemplo oficial) e de mensagem clara quando não houver alternativa.
- Cota de 2.000 requisições/dia estoura fácil se o frontend recalcular a rota a cada interação. Sem debounce + cache no backend, a aplicação pode ficar fora do ar no dia da apresentação (HTTP 403 até a virada do dia).
- Chave de API do ORS exposta no frontend React: se o React chamar a api.openrouteservice.org diretamente, a chave vai no bundle e qualquer pessoa pode queimar a cota. A chamada precisa passar pelo backend.
- Escolher GraphHopper esperando um perfil wheelchair pronto é uma armadilha: ele foi removido na 9.0 e teria que ser reescrito como custom model do zero, o que é um projeto em si — inviável no prazo de um semestre.
- Escolher OSRM significa reprocessar o grafo (osrm-extract + osrm-contract) toda vez que uma barreira for cadastrada — arquitetonicamente incompatível com um sistema colaborativo em tempo real.
- Construir o roteador do zero com OSMnx/NetworkX ou pgRouting consome praticamente todo o tempo da equipe em grafo e algoritmo, sobrando pouco para o que a disciplina realmente avalia (o cadastro colaborativo e a acessibilidade WCAG/eMAG do próprio site).
- Auto-hospedar o ORS com elevação ligada pode falhar de saída: há bug conhecido de que a URL do provedor CGIAR ficou offline e o ORS lança erro quando CGIAR ou MULTI estão configurados. Testar com antecedência e ter provider alternativo.
- Declividade estimada a partir de SRTM 30 m é grosseira demais para acessibilidade de calçada; usar esse número como se fosse a inclinação real da rampa é um erro metodológico que a banca pode apontar. Ou use o MDT do GeoSampa, ou apresente o dado como indicativo, não como medição.
- Serviços gratuitos de hospedagem (Render/Railway/Fly free tier) normalmente não têm os 4-8 GB de RAM que uma instância própria do ORS pede — o plano B de auto-hospedar pode ficar restrito à máquina de um integrante, o que é frágil no dia da apresentação.
- Barreiras reportadas por usuários sem moderação podem ser usadas para vandalismo ou conter erro de geolocalização; sem um mínimo de validação (N confirmações, votação, expiração temporal) o roteador degrada com o tempo.

## Recomendações para o projeto
- RECOMENDAÇÃO PRINCIPAL: usar a API pública do OpenRouteService com o perfil `wheelchair` como motor de roteamento, sem auto-hospedar no MVP. É o único motor com perfil cadeirante pronto, documentado e gratuito, e ele já aceita, em tempo de requisição, tudo que o projeto precisa: `avoid_features:["steps"]`, `avoid_polygons` para as barreiras do banco e `profile_params.restrictions` para preferências do usuário.
- Backend em Python (FastAPI ou Flask) com openrouteservice-py + shapely + pyproj. É a combinação com menos atrito: o cliente Python é oficial e o exemplo oficial de 'avoid obstacles' da própria ORS já é escrito nessa stack — dá para adaptar quase linha a linha. Isso também confirma a intuição do usuário de que Python é mais fácil aqui, e nesse caso a intuição está tecnicamente correta, não é só preferência.
- Implementar o fluxo de duas passadas do exemplo oficial do ORS: (1) pedir a rota inicial só com o perfil wheelchair; (2) consultar no PostGIS quais barreiras validadas interceptam um buffer de ~50 m ao redor dessa rota; (3) transformar essas barreiras em polígonos (buffer de 5-10 m em UTM 23S / EPSG:31983, depois reprojetar para WGS84); (4) refazer a requisição com `avoid_polygons`. Isso mantém o número de polígonos pequeno e a requisição dentro dos limites.
- Modelar severidade da barreira no seu lado, já que o ORS só faz bloqueio duro: barreira 'intransponível' (escada, buraco, ausência de rampa) com N confirmações vira polígono em avoid_polygons; barreira 'dificulta' (piso irregular, calçada estreita) não bloqueia, mas é exibida como aviso na rota e usada para ordenar rotas alternativas (peça `alternative_routes` e ranqueie pela contagem de barreiras leves atravessadas). Essa é a lógica de negócio própria do projeto — é o que diferencia o trabalho de um simples wrapper de API.
- Sempre usar POST, nunca GET, para as requisições de directions — polígonos em GeoJSON estouram o limite de tamanho de URL rapidamente.
- Nunca chamar a ORS direto do React: a chave de API precisa ficar no backend, em variável de ambiente, com o backend expondo o próprio endpoint /api/rotas. Isso também é o ponto natural para colocar cache e debounce.
- Cache obrigatório no backend para não queimar as 2.000 requisições/dia: chavear por (origem arredondada a ~5 casas, destino arredondado, restrições do perfil, hash do conjunto de barreiras relevantes) com TTL de algumas horas. Invalidar o cache quando uma barreira nova for validada naquela região.
- Fallback progressivo quando a rota não for encontrada: tentar maximum_incline=3 → 6 → 10 → any e relaxar smoothness/surface em degraus, informando na interface qual nível de exigência foi atendido ('não encontramos rota com inclinação até 3%; esta rota tem trechos de até 6%'). Isso evita o cenário de tela vazia na apresentação e é, por si só, uma feature de acessibilidade honesta.
- Plano B documentado (bom para a seção de arquitetura do trabalho, mesmo que não seja executado): subir o ORS em Docker com recorte do município de São Paulo feito por `osmium extract` a partir do sudeste-latest.osm.pbf. Isso remove todos os limites de cota e permite editar maximum_avoid_polygon_area/extent no ors-config.yml. Reservar ~4-8 GB de RAM e testar isso com semanas de antecedência, não na véspera.
- Para declividade, adotar abordagem em dois níveis: (a) pedir `elevation:true` nas requisições do ORS — a resposta já vem com coordenadas 3D e permite calcular o perfil de subida da rota sem nenhuma chamada extra; (b) se precisar de declividade pontual para classificar barreiras, usar o Open Topo Data público (SRTM 30 m, sem chave, 1.000 chamadas/dia, 100 pontos por chamada) com cache no banco. Não gastar cota recalculando o mesmo trecho.
- Tratar o MDT LiDAR do GeoSampa (10 pontos/m², 2020) como diferencial acadêmico opcional, não como dependência do MVP: processar offline algumas quadrículas da área piloto, extrair declividade por segmento de calçada e gravar como coluna no PostGIS. Isso rende uma seção forte no relatório (dado oficial municipal de precisão centimétrica vs. SRTM global de 30 m) sem colocar o cronograma em risco.
- Delimitar uma área piloto (ex.: um distrito ou o entorno de uma estação de metrô) em vez de tentar cobrir São Paulo inteira. Reduz o esforço de coleta de barreiras, torna a demo densa o suficiente para o roteamento alternativo aparecer de verdade, e é uma decisão de escopo defensável na banca.
- Não escolher OSRM. O perfil Lua só existe em tempo de pré-processamento e cada barreira nova exigiria osrm-extract + osrm-contract — incompatível com um sistema colaborativo.
- Não escolher GraphHopper para este projeto, apesar de o mecanismo de `areas` em custom_model ser tecnicamente o mais elegante para penalidade graduada: o veículo wheelchair foi removido na 9.0 e teria que ser reescrito do zero como custom model, o que consome o semestre. Vale citar no relatório como trabalho futuro / alternativa avaliada.
- Guardar pgRouting e OSMnx/NetworkX como ferramentas de análise, não como o roteador de produção: pgRouting é excelente para responder consultas espaciais sobre as barreiras (quais interceptam a rota, quantas por bairro) e OSMnx é ótimo para gerar estatísticas e mapas para o relatório. Usar cada um no que é forte, em vez de reimplementar o roteador.

## Implicações para a escolha de backend
Este tema é, de longe, o argumento mais forte a favor de Python — e a escolha não deveria ser tratada como questão de gosto.

PYTHON (recomendado). O ORS mantém cliente oficial em Python (openrouteservice-py) e, mais importante, o exemplo oficial de "avoid obstacles while routing" — que é literalmente o caso de uso deste projeto — está escrito em Python com openrouteservice-py + shapely + pyproj + folium. A equipe consegue partir de código de referência oficial em vez de traduzir. Além disso, todo o ecossistema geoespacial de apoio é Python-first: shapely (buffers e interseções), pyproj (WGS84 ↔ SIRGAS 2000 / UTM 23S, EPSG:31983, necessário para fazer buffer em metros de verdade), geopandas, rasterio (para ler o MDT do GeoSampa), OSMnx (análises e mapas do relatório), psycopg + GeoAlchemy2 (PostGIS). Se um dia quiserem trocar de motor, ainda existe pyvalhalla. Com FastAPI se ganha ainda documentação OpenAPI automática e tipagem via Pydantic, o que casa bem com o frontend React + TypeScript (dá para gerar tipos do schema OpenAPI).

JAVA (segunda opção, com uma vantagem específica). O próprio ORS é uma aplicação Java/Spring Boot, e o GraphHopper é Java e pode ser embutido como biblioteca dentro da aplicação — sem camada HTTP, com latência de poucos milissegundos. Se o objetivo fosse fazer contribuição real ao motor (implementar um custom model de cadeirante no GraphHopper, ou estender o perfil wheelchair do ORS), Java seria a escolha certa e renderia um trabalho de maior profundidade técnica. Para geometria existe o JTS (equivalente maduro do shapely). O custo é o tempo: montar Spring Boot + JTS + build do grafo + reescrever um perfil de acessibilidade é muito mais trabalho por unidade de resultado visível, e o risco de não terminar no semestre é alto para uma equipe pequena.

C# / .NET (não recomendado para este tema). Não há cliente oficial do ORS para .NET, nem motor de roteamento OSM maduro nativo em C# — o backend ficaria reduzido a chamadas REST com HttpClient e desserialização manual. Existe o NetTopologySuite, que é uma porta competente do JTS e resolve a parte de geometria (buffers, interseções, GeoJSON) razoavelmente bem, e o Npgsql tem bom suporte a PostGIS. Ou seja: é viável, não é confortável. Cada peça de apoio (leitura de raster de elevação, processamento de PBF, análise de grafo) exigiria uma solução própria ou uma biblioteca menos mantida. A escolha só se justificaria se a equipe já tivesse domínio forte de C# e a disciplina exigisse.

CONCLUSÃO: para "consumir o ORS com perfil wheelchair, transformar barreiras do banco em polígonos e devolver rota ao React", Python entrega o caminho mais curto entre a proposta e um sistema funcionando, com código de referência oficial disponível. A preferência do usuário por Python coincide com a decisão tecnicamente correta neste caso específico — o que é uma boa notícia, mas vale registrar no relatório com esta justificativa técnica, e não como preferência pessoal.
