# Pesquisa: OpenStreetMap + Overpass API para acessibilidade em São Paulo (tags, consultas, limites, licença e alternativas de processamento local)

## Resumo original
O OpenStreetMap tem um vocabulário maduro de tags de acessibilidade (wheelchair, kerb, tactile_paving, highway=steps, incline, surface, smoothness, width, crossing, highway=elevator, entrance) e a Overpass API permite consultá-lo por bbox ou por área administrativa com sintaxe simples. Medi a cobertura real na cidade de São Paulo executando consultas Overpass durante esta pesquisa: existem cerca de 7.846 objetos com wheelchair=*, 6.174 nós com kerb=*, 5.214 com tactile_paving=* e 3.652 escadarias (highway=steps) — números úteis, mas muito desiguais. O ponto crítico é que apenas 1,9% das 54.211 travessias mapeadas têm kerb=* (informação de guia rebaixada), só 185 das 3.652 escadas informam ramp=*, e smoothness aparece em apenas 51 vias pedonais de toda a cidade. Ou seja: há dados suficientes para um protótipo acadêmico convincente, mas não para roteamento acessível confiável sem a camada colaborativa que o projeto propõe — o que, na verdade, justifica o projeto. A política oficial da Overpass proíbe explicitamente usar instâncias públicas como backend de aplicação em produção, e durante os testes as instâncias overpass-api.de, kumi.systems e private.coffee retornaram erro de sobrecarga várias vezes; uma consulta realista de 4x4 km no centro levou 12,4 segundos e devolveu 432 KB. A alternativa correta é baixar o extrato Geofabrik do Sudeste (857 MB, atualizado diariamente) e processá-lo localmente, carregando o resultado em PostgreSQL/PostGIS. Descobri também que o espelho kumi.systems está com dados de 01/06/2026, três meses defasados, enquanto o overpass-api.de estava atualizado ao segundo. Para roteamento, o OpenRouteService oferece um perfil wheelchair nativo com parâmetros de inclinação máxima, altura de guia e largura mínima, em plano gratuito de aproximadamente 2.000 requisições/dia. A licença ODbL exige atribuição visível e impõe share-alike caso o projeto publique um banco derivado. A API clássica do Wheelmap está desligada (conexão recusada) e sua sucessora accessibility.cloud exige token institucional via wheelmap.pro, o que a torna pouco prática para um projeto acadêmico. Todo esse conjunto favorece Python no backend, pelo ecossistema geoespacial (pyrosm, pyosmium, OSMnx, GeoPandas, Shapely) que não tem equivalente em maturidade no Java ou no C#.

## Resumo corrigido pelo verificador (confiabilidade 7.5/10)
Este relatório é incomumente honesto na parte empírica e descuidado na parte normativa. Reexecutei hoje, em overpass-api.de, todas as contagens de São Paulo que ele apresenta, e elas se sustentam: wheelchair 8.072 (relatório: 7.846), crossings 54.954 (54.211), kerb 6.190 (6.174), steps 3.713 (3.652), tactile_paving 5.226 (5.214), elevadores 86 (86, idêntico) — divergências de 1% a 3%, coerentes com três meses de mapeamento. O argumento central sobrevive intacto e é reproduzível pela banca: apenas 1.035 das 54.954 travessias de SP têm kerb=* (1,9%), somente 185 das 3.713 escadas informam ramp=*, e smoothness existe em 52 vias pedonais na cidade inteira. Isso justifica tecnicamente a camada colaborativa do projeto e deve ir para a fundamentação. Os erros estão nas afirmações sobre políticas e limites de terceiros. A Overpass NÃO 'proíbe expressamente' usar instâncias públicas como backend: a documentação usa o rótulo 'problematic behaviour' e recomenda alternativas — a conclusão prática está certa, a justificativa jurídica não, e a frase entre aspas no relatório não existe no original. No OpenRouteService, o perfil wheelchair tem 6.000 km de distância máxima como os demais; os 300 km valem apenas quando se enviam profile_params (que é o caso deste projeto, mas a formulação está errada); e as cotas do plano gratuito são POR ENDPOINT (directions: 2.000/dia e 40/minuto; HTTP 403 no estouro diário, 429 no por minuto), não cumulativas como o relatório afirma citando uma fonte que diz outra coisa. O diagnóstico do espelho kumi.systems está errado de um jeito que na verdade agrava o risco: quatro consultas consecutivas minhas devolveram quatro timestamp_osm_base diferentes (24/07, 31/05, 28/07 e 01/06 de 2026), porque é um cluster com workers de datas distintas — logo, a mesma consulta pode render contagens diferentes, o que destrói reprodutibilidade. Pior: kumi.systems e private.coffee retornaram o mesmo ID de conexão e os mesmos PIDs em execução, ou seja, são a mesma infraestrutura e não servem de plano B um para o outro. Dois exemplos de código estão quebrados e precisam ser corrigidos antes de irem para a entrega: a 'consulta central do projeto' usa {{bbox}}, que é template do overpass-turbo e retorna 'parse error: Unknown query clause' no endpoint real (testei), e o exemplo do OSMnx usa a assinatura posicional removida na versão 2.0, que hoje exige bbox=(oeste, sul, leste, norte) numa tupla única. Há ainda uma inconsistência aritmética interna — a distribuição de valores wheelchair soma 7.911 sobre um total declarado de 7.846, o que é impossível; os valores reais de hoje são yes 5.097, no 1.898, limited 1.042, designated 31. Confirmei ao byte os extratos Geofabrik (856.923.881 e 2.081.927.879 bytes, ambos de 07/09/2026), todos os defaults do perfil wheelchair do ORS, as citações literais das políticas de Nominatim, tiles e atribuição, os limiares de 7 cm do wheelchair e as alturas de kerb — e reproduzi ao vivo tanto o erro de sobrecarga 'Dispatcher_Client::request_read_and_idx::timeout' quanto o retorno zero de overpass.osm.ch para São Paulo. As lacunas mais caras são de escopo, não de exatidão: a SPTrans Olho Vivo, que era uma das duas APIs da proposta original, não aparece em lugar nenhum; o GeoSampa, base oficial da Prefeitura de São Paulo, não é avaliado, o que enfraquece a conclusão de que 'os dados são insuficientes'; o Photon é omitido justamente onde o relatório proíbe autocomplete no Nominatim sem oferecer a alternativa padrão (atenção: o Photon rejeita lang=pt, use lang=default); pgRouting e GraphHopper autohospedado não são cogitados, embora resolveriam a dependência de cota externa que o próprio relatório aponta como risco de dia de apresentação; e a distinção ODbL entre Collective Database e Derivative Database, que decidiria se o share-alike contamina ou não os dados próprios do grupo, não é discutida. A omissão mais grave para a nota é outra: um relatório sobre um projeto de acessibilidade não diz nada sobre como tornar o próprio mapa navegável por teclado e utilizável com leitor de tela, nem sobre a necessidade de uma alternativa textual completa à rota — que é o único caminho realista de conformidade WCAG/eMAG para conteúdo cartográfico. As recomendações de arquitetura (pré-processar o extrato Geofabrik com osmium, carregar em PostGIS, nunca chamar a Overpass no caminho da requisição, tratar barreiras colaborativas como camada de penalização no grafo, separar wheelchair de POI de barreira de percurso, suportar os dois esquemas de calçada) permanecem sólidas e verificadas, assim como o veredito a favor do Python — que se sustenta pelo ecossistema (pyrosm 12x mais rápido que OSMnx em POIs, 4,3 s contra 52,9 s, confirmado), ainda que a URL citada para esse benchmark esteja morta e precise ser trocada por github.com/pyrosm/pyrosm.

## Afirmações refutadas
- **A política oficial da Overpass API 'proíbe expressamente' / 'proíbe explicitamente' usar instâncias públicas como backend de aplicação em produção.**
  - Motivo: Busquei o texto literal em dev.overpass-api.de/overpass-doc/en/preface/commons.html. O documento NÃO usa 'prohibited' nem 'forbidden'. Ele classifica os casos sob o rótulo 'problematic behaviour' e, em seguida, RECOMENDA soluções (usar planet dumps, hospedar instância própria). Além disso, a frase citada entre aspas pelo relatório não existe: o texto real é 'Setting up an app for more than just OSM mappers and relying on the public instances as backend' — não há a palavra 'production' em lugar nenhum, nem menção a 'produção'. O relatório transformou uma diretriz de boa vizinhança em proibição normativa e apresentou paráfrase como citação literal.
  - Correção: A Overpass lista como 'comportamento problemático' (problematic behaviour): 'Setting up an app for more than just OSM mappers and relying on the public instances as backend', 'Stiching bounding boxes to scrape the full data of the complete world' e 'Asking for individual OSM elements one by one millions of times'. É uma recomendação forte, não uma proibição contratual. A conclusão prática do relatório (não chamar a Overpass no caminho da requisição do usuário) continua correta — só não deve ser justificada como 'violação de política'.
  - Fonte: https://dev.overpass-api.de/overpass-doc/en/preface/commons.html
- **O perfil wheelchair do ORS tem distância máxima de 300 km por rota, contra 6.000 km dos demais perfis.**
  - Motivo: Transcrevi a tabela de openrouteservice.org/restrictions/. Ela tem DUAS colunas: 'Maximum distance' e 'Maximum distance with profile restrictions'. O perfil wheelchair tem 6.000 km na primeira coluna, igual a todos os outros. Os 300 km aparecem apenas na segunda coluna — ou seja, só valem quando o request usa profile_params/restrictions. E os demais perfis têm 6.000 km em AMBAS as colunas, não só na primeira.
  - Correção: Wheelchair: 6.000 km sem restrições de perfil, 300 km QUANDO se enviam profile_params/restrictions (que é justamente o caso deste projeto). Foot/cycling/driving: 6.000 km nas duas situações. O efeito prático (irrelevante para uso urbano) permanece, mas a formulação está errada.
  - Fonte: https://openrouteservice.org/restrictions/
- **No plano gratuito do ORS, as cotas são 'cumulativas entre endpoints' (~2.000 req/dia compartilhadas).**
  - Motivo: Duas evidências contra. (1) A FAQ oficial do backend diz 'endpoints have a daily and a minutely request limit' — no plural, por endpoint, e exemplifica directions com 'default limit of 2000 requests per day' e 'any consecutive period of 60 seconds may only contain 40 directions requests' (note: '40 DIRECTIONS requests', qualificado pelo endpoint). (2) A fonte que o próprio relatório cita, ask.openrouteservice.org/t/updated-api-quotas/500, não menciona cotas cumulativas nem o número 2.000 — ela fala em 'a total of > 8000 requests per day' mais 20.000 tiles. A citação está mal atribuída.
  - Correção: Cada endpoint tem cota diária e por minuto PRÓPRIAS. Directions no plano gratuito: 2.000/dia e 40/minuto em janela deslizante. Estouro da cota diária retorna HTTP 403 (não 429); estouro do limite por minuto retorna HTTP 429. O saldo pode ser lido nos headers x-ratelimit-remaining e x-ratelimit-reset — vale instrumentar isso no backend.
  - Fonte: https://giscience.github.io/openrouteservice/frequently-asked-questions
- **O espelho overpass.kumi.systems 'está com dados de 01/06/2026, três meses defasados'.**
  - Motivo: Refutado por medição direta, e o problema real é PIOR do que o descrito. Fiz quatro consultas consecutivas ao kumi hoje (08/09/2026) e recebi quatro timestamp_osm_base DIFERENTES: 2026-07-24T11:04:51Z, 2026-05-31T22:37:44Z, 2026-07-28T02:16:18Z e 2026-06-01T08:52:28Z. O kumi é um cluster com balanceamento de carga (header Kumi-Overpass-Worker: h8) e cada worker tem uma data de dados distinta. O valor exato citado pelo relatório é real, mas é de UM worker, não do espelho.
  - Correção: O kumi.systems não tem 'uma' data de dados: ele distribui consultas entre workers cujos snapshots variam de ~6 semanas a ~3,5 meses de atraso. Consequência prática mais grave do que o relatório afirma: duas execuções idênticas da MESMA consulta podem retornar contagens diferentes, o que inviabiliza reprodutibilidade de estatísticas acadêmicas. Para qualquer número que vá para o relatório da disciplina, use exclusivamente overpass-api.de (verificado hoje com timestamp_osm_base 2026-09-08T22:26:06Z, atualizado ao minuto).
  - Fonte: Medição própria: 4 chamadas consecutivas a https://overpass.kumi.systems/api/interpreter em 08/09/2026
- **overpass.kumi.systems e overpass.private.coffee são espelhos alternativos distintos, úteis como plano B um do outro.**
  - Motivo: Consultei /api/status dos dois com poucos segundos de diferença. Ambos retornaram o MESMO 'Connected as: 175833359', o mesmo 'Announced endpoint: none', o mesmo 'Rate limit: 0' e — decisivo — a MESMA lista de PIDs de consultas em execução (3063291, 3063295, 3062133...). Não são instâncias independentes: private.coffee resolve para a mesma infraestrutura do kumi.
  - Correção: kumi.systems e private.coffee compartilham backend. Alternar entre eles NÃO oferece redundância: se um estiver sobrecarregado, o outro estará também. A única redundância real verificada é entre overpass-api.de e o cluster kumi/private.coffee. (overpass.osm.ch não conta — confirmei que retorna 0 para São Paulo, é extrato regional suíço.)
  - Fonte: Comparação própria de https://overpass.kumi.systems/api/status e https://overpass.private.coffee/api/status em 08/09/2026
- **A distribuição de valores wheelchair em SP é: yes 5.015, no 1.833, limited 1.042, designated 21, sobre um total de 7.846 objetos.**
  - Motivo: Inconsistência aritmética interna: 5.015 + 1.833 + 1.042 + 21 = 7.911, que é MAIOR que o total declarado de 7.846. Como cada objeto tem no máximo um valor de wheelchair, a soma dos valores nunca pode exceder o total. Pelo menos um dos cinco números é falso. Remedi hoje na mesma bbox em overpass-api.de.
  - Correção: Valores reais em 08/09/2026 (bbox -23.82,-46.83,-23.36,-46.36, overpass-api.de): total nwr[wheelchair] = 8.072; yes = 5.097; no = 1.898; limited = 1.042; designated = 31. Soma dos valores = 8.068, coerente com o total (4 objetos com valores atípicos). Use estes números.
  - Fonte: Consulta Overpass própria (out count) em https://overpass-api.de/api/interpreter, 08/09/2026
- **Exemplo de 'Consulta Overpass de barreiras físicas': way["highway"="steps"]({{bbox}}); ... via POST no /api/interpreter.**
  - Motivo: {{bbox}} é um atalho de TEMPLATE do overpass-turbo (a IDE web), não sintaxe válida de Overpass QL. Enviei exatamente esse exemplo ao endpoint real e recebi: 'line 1: parse error: Unknown query clause'. O relatório apresenta a consulta como corpo de um POST ao interpreter, onde ela falha 100% das vezes. É a 'consulta central do projeto' segundo o próprio relatório, então o erro é caro.
  - Correção: No overpass-turbo o {{bbox}} funciona; no /api/interpreter é preciso substituir por coordenadas literais (sul,oeste,norte,leste), por uma bbox global no cabeçalho ([bbox:...]) ou por um parâmetro de query string. Ex.: way["highway"="steps"](-23.57,-46.66,-23.53,-46.62);. No backend, interpole as coordenadas por template string antes de enviar.
  - Fonte: Teste próprio contra https://overpass-api.de/api/interpreter em 08/09/2026 (resposta: parse error: Unknown query clause)
- **Exemplo OSMnx: G = ox.graph_from_bbox(-23.53,-23.57,-46.62,-46.66, network_type='walk')**
  - Motivo: Essa é a assinatura antiga (north, south, east, west como posicionais), removida no OSMnx 2.0. A documentação atual (osmnx.readthedocs.io/en/stable/user-reference.html) especifica: 'bbox (tuple[float, float, float, float]) – Bounding box as (left, bottom, right, top)'. O código do relatório levanta TypeError em qualquer instalação recente do OSMnx, e a ordem das coordenadas também está trocada em relação ao novo formato.
  - Correção: Na API atual: G = ox.graph_from_bbox(bbox=(-46.66, -23.57, -46.62, -23.53), network_type='walk') — ou seja (oeste, sul, leste, norte) numa única tupla. Fixe a versão no requirements.txt (osmnx>=2.0) e teste o exemplo antes de colocá-lo no relatório da disciplina.
  - Fonte: https://osmnx.readthedocs.io/en/stable/user-reference.html
- **A API clássica do Wheelmap está fora do ar: 'a conexão é recusada (ECONNREFUSED 176.9.63.170:443)'.**
  - Motivo: A conclusão está certa, mas o mecanismo relatado não se reproduz. Testei classic.wheelmap.org hoje: o host RESOLVE normalmente e a conexão fica pendurada até estourar o tempo (curl: 'Connection timed out after 20014 milliseconds', exit 28). Timeout de conexão é comportamento diferente de ECONNREFUSED (que retornaria RST imediato, exit 7). O IP específico 176.9.63.170 citado é um detalhe que não consegui reproduzir e que tem cara de alucinação de precisão.
  - Correção: classic.wheelmap.org está inacessível por timeout de conexão, não por recusa. O domínio principal wheelmap.org responde (HTTP 403 para curl, provavelmente proteção anti-bot), então o projeto Wheelmap não está morto — só a API clássica. A recomendação de descartar a integração permanece válida: confirmei o erro do sucessor literalmente — {"error":{"reason":"Please supply a token.","details":"...Log in on https://wheelmap.pro/ to obtain a valid token in organization's API client settings."}}
  - Fonte: Testes próprios contra classic.wheelmap.org, wheelmap.org e accessibility-cloud-v2.freetls.fastly.net em 08/09/2026
- **Fonte do benchmark do pyrosm: https://pyrosm.readthedocs.io/en/latest/benchmarking.html**
  - Motivo: A URL citada retorna HTTP 404 hoje, tanto via curl quanto via fetch. Testei também /benchmarks.html (404) e /basics.html (404); só a raiz /en/latest/ responde 200. A documentação do pyrosm foi reorganizada e os links do relatório estão quebrados — um problema real para a bibliografia de um trabalho acadêmico.
  - Correção: Os NÚMEROS estão corretos e continuam confirmáveis (POIs: 4,3 s no pyrosm contra 52,9 s no OSMnx, ~12x; vias: 3,2 s contra 78,3 s, ~24x; pyrosm escrito em Cython; OSMnx lê via Overpass pela internet enquanto pyrosm lê dump PBF local — este último ponto está textualmente no README do GitHub). Mas cite https://github.com/pyrosm/pyrosm e https://pyrosm.readthedocs.io/en/latest/ em vez da URL morta, e verifique cada link antes da entrega.
  - Fonte: Verificação própria de códigos HTTP em 08/09/2026 + https://github.com/pyrosm/pyrosm/blob/master/README.md
- **Valores de kerb a tratar no parsing: lowered, flush, raised e rolled.**
  - Motivo: Lista incompleta, e os próprios números do relatório denunciam isso: 3.867 + 1.699 + 590 = 6.156, contra um total declarado de 6.174 nós com kerb. Sobram 18 objetos sem classificação. O wiki documenta também kerb=yes ('any' — altura indeterminada) e kerb=no (ausência de guia). Na minha medição de hoje a lacuna se mantém: 6.190 nós no total contra 6.167 em lowered/raised/flush.
  - Correção: Trate cinco valores no parser: flush (~0 cm) e lowered (≲3 cm) como transponíveis; raised (>3 cm) e rolled como barreira; kerb=no como ausência de guia (transponível); e kerb=yes como DESCONHECIDO — nunca como acessível, porque significa apenas que existe uma guia de altura não determinada. O wiki avisa que 'heights given here are only indicative'.
  - Fonte: https://wiki.openstreetmap.org/wiki/Key:kerb + consulta Overpass própria 08/09/2026

## Lacunas apontadas
- SPTrans Olho Vivo está inteiramente ausente. Era uma das duas APIs nomeadas na proposta do projeto e o relatório não a menciona uma única vez. Faltam: o fluxo de autenticação (token no portal de desenvolvedores, endpoint POST /Login/Autenticar que devolve cookie de sessão — verifiquei que sptrans.com.br/desenvolvedores/ responde HTTP 200), o fato de que a Olho Vivo entrega posição de veículos e previsão de chegada mas NÃO expõe de forma confiável se o veículo específico é acessível, e a consequência de projeto: a acessibilidade do ônibus precisa vir do OSM (wheelchair em public_transport=platform, onde medi apenas 12,8% de cobertura) ou da camada colaborativa.
- GeoSampa não é citado. É o portal oficial de geodados da Prefeitura de São Paulo (verifiquei: responde HTTP 200) e publica camadas municipais em shapefile/WFS — logradouros, quadras, mobiliário urbano, equipamentos públicos — potencialmente com cobertura superior ao OSM justamente na periferia, onde o relatório identifica o pior viés. Um relatório que conclui 'os dados OSM são insuficientes' sem avaliar a base oficial do município tem um buraco metodológico grande, e citar fonte municipal oficial vale ponto na avaliação acadêmica.
- Photon não é mencionado, apesar de o relatório dedicar um risco inteiro ao 'Nominatim em autocomplete'. O Photon (photon.komoot.io) é o geocodificador baseado em OSM construído EXATAMENTE para autocomplete tecla a tecla, é gratuito e autohospedável. Testei hoje e responde normalmente. Ressalva verificada e importante: ele rejeita lang=pt — retorna 'Language is not supported. Supported are: default, de, en, fr' — então use lang=default para endereços brasileiros. O relatório aponta o problema e omite a solução padrão da comunidade.
- Nenhuma alternativa de roteamento local é discutida. O relatório apresenta um falso dilema: 'usar o ORS ou implementar do zero'. Ficaram de fora pgRouting (extensão do PostGIS que o projeto já vai instalar, elimina totalmente a dependência de cota externa), Valhalla e o GraphHopper autohospedado — este último é especialmente relevante porque o próprio relatório observa que o ORS é construído sobre GraphHopper. Para um projeto que teme estourar 2.000 requisições/dia em dia de apresentação, isso é uma omissão prática.
- A distinção ODbL entre Produced Work, Derivative Database e Collective Database não é abordada. É decisiva para a arquitetura: se as barreiras cadastradas pelos usuários ficarem em tabela SEPARADA, apenas justaposta aos dados OSM, o conjunto tende a ser um Collective Database e o share-alike NÃO contamina os dados próprios do grupo; se forem mescladas num banco único derivado, contamina. O relatório trata o share-alike como inevitável e perde uma decisão de modelagem que custa quase nada tomar corretamente no início.
- Não há nada sobre devolver dados ao OSM. Um sistema colaborativo de barreiras deveria, no mínimo, discutir se as barreiras reportadas serão contribuídas de volta via API 0.6 / changesets, e os problemas associados: a proveniência dos reportes dos usuários é compatível com a cessão exigida pelos Contributor Terms do OSM? O relatório não levanta a questão, que é simultaneamente técnica, jurídica e um ótimo tópico de discussão acadêmica.
- Falta a estratégia de atualização incremental. O relatório recomenda um download único de 857 MB e um vago 'job semanal via Overpass'. O mecanismo padrão nem é nomeado: diffs do Geofabrik consumidos por pyosmium-up-to-date, ou osm2pgsql --append com --slim (que o próprio exemplo de comando do relatório já habilita, sem explicar para quê). Sem isso, o banco do projeto congela no dia do primeiro carregamento.
- Acessibilidade do próprio mapa é ignorada — e é o item mais grave, porque é justamente o que será avaliado com rigor na disciplina. O relatório não diz uma palavra sobre como tornar um mapa Leaflet/MapLibre navegável por teclado, como expor a rota a leitores de tela, ou sobre a necessidade de uma alternativa textual completa (lista de instruções passo a passo) ao canvas do mapa — que é o único caminho realista de conformidade WCAG/eMAG para conteúdo cartográfico. Um mapa interativo é, por padrão, inacessível para o público-alvo do projeto.
- Nenhuma estimativa de viabilidade da infraestrutura em tier gratuito. Os free tiers de Supabase, Neon e Render têm tetos de armazenamento (tipicamente 0,5 a 1 GB) que um osm2pgsql do Sudeste com --hstore estoura com folga. O relatório recomenda PostgreSQL/PostGIS na nuvem sem checar se o resultado cabe no orçamento zero declarado — falta dimensionar o banco DEPOIS do recorte por bbox e do tags-filter.
- Consultas históricas da Overpass ([date:...], [adiff], attic data) não são mencionadas. Permitiriam medir a EVOLUÇÃO do mapeamento de acessibilidade em SP ao longo do tempo — por exemplo, o impacto do projeto SMPED/SMT de 2021 na Lapa e Vila Mariana. É material de fundamentação acadêmica de alto valor, disponível de graça, e o relatório não sabe que existe.
- Faltam números concretos dos planos B de tiles. O relatório recomenda 'MapTiler ou Stadia Maps' como alternativa sem informar cotas, exigência de cartão ou obrigações de atribuição desses serviços — exatamente o tipo de detalhe que ele apurou com cuidado para todos os demais serviços. O plano B fica não verificado.
- Nenhuma menção a rotas acessíveis já existentes para comparação/baseline (por exemplo o demo wheelchair do próprio ORS, ou o AccessMap da Universidade de Washington, do mesmo Taskar Center citado no relatório). Um trabalho acadêmico se beneficia de comparar a solução proposta com o estado da arte, e o relatório cita o Taskar Center sem mencionar o produto que esse centro construiu.

## Fatos levantados
- [alta] Na cidade de São Paulo (bbox -23.82,-46.83,-23.36,-46.36) existem 7.846 objetos com a tag wheelchair=*: 5.107 nós, 2.292 ways e 447 relations. Distribuição de valores: wheelchair=yes 5.015, wheelchair=no 1.833, wheelchair=limited 1.042, wheelchair=designated 21. (fonte: Consulta Overpass QL executada por mim em 08/09/2026 em https://overpass.kumi.systems/api/interpreter (snapshot de dados 2026-06-01))
- [alta] Existem 54.211 nós highway=crossing em São Paulo, mas apenas 1.029 deles (1,9%) possuem a tag kerb=*. Isso significa que a informação de guia rebaixada, essencial para cadeirantes, está ausente em 98% das travessias mapeadas. (fonte: Consulta Overpass QL executada por mim em 08/09/2026 (overpass.kumi.systems))
- [alta] São Paulo tem 6.174 nós com kerb=*, distribuídos em kerb=lowered 3.867, kerb=raised 1.699 e kerb=flush 590. Segundo o wiki, lowered (até ~3 cm) e flush (~0 cm) são acessíveis para cadeira de rodas; raised (>3 cm) e rolled não são. (fonte: Consulta Overpass própria (08/09/2026) + https://wiki.openstreetmap.org/wiki/Key:kerb)
- [alta] Há 3.652 escadarias (highway=steps) mapeadas em São Paulo, mas apenas 185 (5%) informam a tag ramp=*. Escadas são a barreira física mais bem mapeada da cidade e o dado mais imediatamente aproveitável pelo projeto. (fonte: Consulta Overpass própria (08/09/2026))
- [alta] A tag smoothness (qualidade do piso) aparece em apenas 51 vias pedonais em toda a cidade de São Paulo, contra 23.013 com surface. Na prática, smoothness é inutilizável em SP, apesar de ser o parâmetro que o OpenRouteService usa por padrão no perfil wheelchair. (fonte: Consulta Overpass própria (08/09/2026))
- [alta] São Paulo tem 38.216 ways highway=footway, dos quais apenas 4.703 são explicitamente footway=sidewalk (calçada como geometria própria). Em paralelo, 10.088 vias têm o atributo sidewalk=* na própria rua. Convivem, portanto, dois esquemas de mapeamento incompatíveis para roteamento. (fonte: Consulta Overpass própria (08/09/2026))
- [alta] A comunidade OSM brasileira não tem padrão consolidado para calçadas: Porto Alegre e Salvador usam atributos na via (sidewalk:*), Fortaleza usa geometria separada, e São Paulo apresenta esquemas sobrepostos sem coordenação. Um participante resume o problema local: 'Calçadas com degraus e não padronizadas são regra, não exceção. Em São Paulo é difícil achar um bairro em que não existam degraus'. - [alta] Outros dados de acessibilidade em SP: 5.214 objetos com tactile_paving=* (1.868 com valor yes), 902 ways com incline=*, 889 vias pedonais com width=*, 5.256 objetos com entrance=* e apenas 86 elevadores (highway=elevator). (fonte: Consultas Overpass próprias (08/09/2026))
- [alta] No transporte público de SP: 21.086 objetos public_transport=platform, dos quais 2.705 (12,8%) têm wheelchair=*; e 208 entradas de metrô (railway=subway_entrance), das quais 62 (30%) têm wheelchair=*. As entradas de metrô são o subconjunto mais bem documentado. (fonte: Consultas Overpass próprias (08/09/2026))
- [alta] A política oficial da Overpass API proíbe expressamente 'usar instâncias públicas como backend de aplicação em produção', além de proibir emendar bounding boxes para raspar dados completos e consultar elementos um a um em escala. ## Endpoints / recursos
- **Overpass API — instância principal (interpreter)** — POST https://overpass-api.de/api/interpreter, corpo = texto da consulta Overpass QL, Content-Type: text/plain
  - Retorna: JSON ou CSV com os elementos OSM que casam com os filtros. Dados sempre atualizados (verificado: timestamp ao segundo). Limite de 2 slots simultâneos por IP.
  - Exemplo: `[out:json][timeout:60];
(
  way["highway"="steps"](-23.57,-46.66,-23.53,-46.62);
  node["kerb"="raised"](-23.57,-46.66,-23.53,-46.62);
);
out geom;`
- **Overpass API — status (diagnóstico de cota)** — GET https://overpass-api.de/api/status
  - Retorna: Texto simples com o ID da conexão, o rate limit em slots, quantos slots estão livres agora e a lista de consultas em execução. Use antes de disparar lotes de consultas para evitar HTTP 429.
  - Exemplo: `curl https://overpass-api.de/api/status
# Rate limit: 2
# 2 slots available now.`
- **Consulta Overpass por área administrativa (mais preciso que bbox)** — Usar area[...] para delimitar o município exato em vez de um retângulo
  - Retorna: Somente elementos dentro do limite oficial da cidade de São Paulo, sem incluir municípios vizinhos como Osasco ou Diadema que caem dentro da bbox. Mais lento que bbox — em testes chegou a estourar o dispatcher.
  - Exemplo: `[out:json][timeout:300];
area["name"="São Paulo"]["admin_level"="8"]["boundary"="administrative"]->.sp;
nwr(area.sp)["wheelchair"];
out center;`
- **Consulta Overpass de barreiras físicas (a consulta central do projeto)** — POST no interpreter com união de filtros de barreira
  - Retorna: Todas as barreiras conhecidas do OSM numa região: escadas, guias altas, travessias sem piso tátil e locais marcados como inacessíveis. Benchmark real: 1.093 elementos, 432 KB, 12,4 s numa área de 4x4 km.
  - Exemplo: `[out:json][timeout:90];
(
  way["highway"="steps"]({{bbox}});
  node["kerb"~"^(raised|rolled)$"]({{bbox}});
  nwr["wheelchair"="no"]({{bbox}});
  node["highway"="crossing"]["tactile_paving"="no"]({{bbox}});
  way["incline"]({{bbox}});
);
out geom;`
- **Consulta Overpass de rede pedonal para roteamento** — Filtrar vias pedonais e recursar para os nós com >;
  - Retorna: Geometria completa (ways + nós) da rede caminhável, pronta para montar o grafo de rotas. O operador >; é obrigatório para trazer os nós referenciados pelos ways.
  - Exemplo: `[out:json][timeout:180];
way["highway"~"^(footway|path|pedestrian|steps|living_street|residential)$"]({{bbox}});
>;
out skel qt;`
- **Overpass — saída CSV para contagens e estatísticas** — Prefixo [out:csv(...)] com out count
  - Retorna: Números puros, ideal para medir cobertura de tags por região (foi assim que levantei todas as estatísticas de SP deste relatório). Respostas minúsculas, baratas para o servidor.
  - Exemplo: `[out:csv(::count;false)][timeout:600];
nwr["wheelchair"](-23.82,-46.83,-23.36,-46.36); out count;
node["kerb"="lowered"](-23.82,-46.83,-23.36,-46.36); out count;`
- **Espelhos alternativos da Overpass** — https://overpass.kumi.systems/api/interpreter (sem limite de slots, mas dados de 01/06/2026 — 3 meses defasados); https://overpass.private.coffee/api/interpreter; https://overpass.osm.ch/api/interpreter (ATENÇÃO: só tem dados da Suíça, retorna 0 para SP)
  - Retorna: Mesma API, cobertura e atualidade variáveis. Sempre confira o campo timestamp_osm_base da resposta antes de confiar no espelho.
  - Exemplo: `curl -s -X POST --data-binary @consulta.txt https://overpass.kumi.systems/api/interpreter | grep timestamp_osm_base`
- **Geofabrik — extrato do Sudeste em PBF (alternativa recomendada à Overpass)** — GET https://download.geofabrik.de/south-america/brazil/sudeste-latest.osm.pbf
  - Retorna: Arquivo .osm.pbf de ~857 MB com todo o Sudeste, atualizado diariamente. Sem rate limit, sem risco de indisponibilidade, processável offline. O do Brasil inteiro tem ~2,08 GB.
  - Exemplo: `curl -O https://download.geofabrik.de/south-america/brazil/sudeste-latest.osm.pbf`
- **osmium-tool — recorte e filtragem do extrato** — CLI em C++ (também disponível como pyosmium no Python). Recorta a bbox de SP e filtra só as tags de interesse antes de carregar no banco.
  - Retorna: Um PBF muito menor, contendo só a área e as tags relevantes — reduz drasticamente o tempo de ETL.
  - Exemplo: `osmium extract -b -46.83,-23.82,-46.36,-23.36 sudeste-latest.osm.pbf -o sp.osm.pbf
osmium tags-filter sp.osm.pbf w/highway n/kerb nwr/wheelchair nwr/tactile_paving -o sp-acess.osm.pbf`
- **pyrosm — leitura de PBF direto para GeoPandas (Python)** — pip install pyrosm; lê o .osm.pbf local sem rede
  - Retorna: GeoDataFrames com redes viárias, POIs e atributos personalizados. ~12x mais rápido que OSMnx no benchmark oficial. Melhor opção para o ETL inicial do projeto.
  - Exemplo: `from pyrosm import OSM
osm = OSM('sp-acess.osm.pbf')
nodes, edges = osm.get_network(network_type='walking', nodes=True)
pois = osm.get_data_by_custom_criteria(custom_filter={'wheelchair': True})`
- **OSMnx — grafo de rede pedonal e roteamento (Python)** — pip install osmnx; busca via Overpass ou carrega de arquivo local
  - Retorna: Grafo NetworkX já topologicamente correto, pronto para algoritmos de caminho mínimo com pesos personalizados (é aqui que se aplica a penalização das barreiras colaborativas).
  - Exemplo: `import osmnx as ox, networkx as nx
G = ox.graph_from_bbox(-23.53,-23.57,-46.62,-46.66, network_type='walk')
# aplicar peso extra em arestas com barreira reportada
rota = nx.shortest_path(G, orig, dest, weight='custo_acessivel')`
- **osm2pgsql — carga do PBF em PostgreSQL/PostGIS** — CLI; carrega o extrato num banco espacial com suporte a atualizações incrementais
  - Retorna: Tabelas PostGIS consultáveis por SQL espacial. É a base recomendada para o backend do projeto, permitindo unir dados do OSM com as barreiras cadastradas pelos usuários numa única consulta.
  - Exemplo: `osm2pgsql -d acessibilidade --create --slim -G --hstore sp-acess.osm.pbf`
- **OpenRouteService — perfil de roteamento para cadeira de rodas** — POST https://api.openrouteservice.org/v2/directions/wheelchair/geojson com header Authorization: <sua-chave>. Cadastro gratuito em account.heigit.org.
  - Retorna: Rota em GeoJSON já calculada considerando inclinação, altura de guia, largura e tipo de piso. Evita implementar o motor de rotas do zero. Grátis ~2.000 req/dia, 40/min; máximo de 300 km por rota no perfil wheelchair.
  - Exemplo: `{
  "coordinates": [[-46.6333,-23.5505],[-46.6400,-23.5450]],
  "options": {"profile_params": {"restrictions": {
      "maximum_incline": 6,
      "maximum_sloped_kerb": 0.03,
      "minimum_width": 0.9
  }}}
}`
- **Nominatim — geocodificação (com restrições severas)** — GET https://nominatim.openstreetmap.org/search?q=...&format=json&countrycodes=br&viewbox=... com User-Agent obrigatório
  - Retorna: Coordenadas a partir de endereço. Máximo 1 req/s, PROIBIDO usar em autocomplete, cache local obrigatório. Para a caixa de busca do app, use debounce e só dispare no submit — nunca a cada tecla.
  - Exemplo: `curl -H 'User-Agent: GuiaRotasAcessiveis/1.0 (contato@exemplo.br)' \
  'https://nominatim.openstreetmap.org/search?q=Avenida+Paulista,+Sao+Paulo&format=json&limit=5&countrycodes=br'`
- **Taginfo — estatísticas de uso de tags** — https://taginfo.openstreetmap.org/keys/wheelchair (global) e API em https://taginfo.openstreetmap.org/api/4/key/values?key=wheelchair
  - Retorna: Contagens globais e distribuição de valores de qualquer tag. Útil para validar quais valores realmente existem antes de codificar o parser. Para recortes regionais, prefira medir com Overpass out count (como fiz aqui).
  - Exemplo: `curl 'https://taginfo.openstreetmap.org/api/4/key/values?key=kerb'`
- **accessibility.cloud / Wheelmap (fonte complementar — pouco viável)** — https://accessibility-cloud-v2.freetls.fastly.net/place-infos.json?latitude=..&longitude=..&accuracy=..&appToken=<token>. Token obtido só via cadastro organizacional em https://wheelmap.pro/
  - Retorna: POIs com acessibilidade no padrão A11yJSON. A API clássica (classic.wheelmap.org) está desligada. Como o Wheelmap sincroniza com o OSM, o ganho marginal sobre consultar wheelchair=* direto no OSM é pequeno.
  - Exemplo: `curl 'https://accessibility-cloud-v2.freetls.fastly.net/place-infos.json?latitude=-23.55&longitude=-46.63&accuracy=500&appToken=SEU_TOKEN'`
- **Tiles do mapa base para o frontend React** — https://tile.openstreetmap.org/{z}/{x}/{y}.png via react-leaflet ou MapLibre GL
  - Retorna: Imagens do mapa. Exige User-Agent próprio, cache ≥7 dias e atribuição visível; proibido pre-seeding e uso offline. O acesso pode ser cortado sem aviso — tenha um plano B (MapTiler ou Stadia Maps têm planos gratuitos).
  - Exemplo: `<TileLayer
  url="https://tile.openstreetmap.org/{z}/{x}/{y}.png"
  attribution='&copy; <a href="https://www.openstreetmap.org/copyright">OpenStreetMap</a> contributors'
/>`

## Limites e custos
CUSTO FINANCEIRO: zero em todos os serviços listados. Nenhum exige cartão de crédito. Compatível com o orçamento zero do projeto.

CADASTRO E CHAVES:
- Overpass API: sem cadastro, sem chave. Identificação por IP.
- Geofabrik (extratos PBF): sem cadastro, download livre.
- Nominatim público: sem chave, mas User-Agent identificando a aplicação é obrigatório.
- Tiles OSM: sem chave, mas User-Agent próprio obrigatório.
- OpenRouteService: chave obrigatória e gratuita (cadastro em account.heigit.org). Testei sem chave e a resposta foi {"error": "Authorization field missing"}. É a única chave a monitorar no projeto, além da do Gemini.
- accessibility.cloud/Wheelmap: token via cadastro ORGANIZACIONAL em wheelmap.pro — não é self-service, pode levar dias ou não ser aprovado para um trabalho de faculdade.

LIMITES DA OVERPASS (medidos e documentados):
- ~10.000 requisições/dia e <1 GB de download/dia por IP.
- overpass-api.de: apenas 2 slots simultâneos por IP (verificado no /api/status). Excesso retorna HTTP 429 após esperar até 15 s por um slot.
- Timeout padrão 180 s, memória padrão 512 MiB por consulta; o servidor só aceita a consulta se ela couber em metade dos recursos livres. Estouro retorna HTTP 504.
- Disponibilidade instável na prática: obtive o erro "server is probably too busy" em várias tentativas seguidas em três instâncias diferentes durante esta pesquisa.
- Latência real medida: 12,4 s para uma área de 4x4 km com 4 filtros (432 KB de resposta).

PROIBIÇÃO DECISIVA: a política oficial lista "usar instâncias públicas como backend de aplicação em produção" entre os comportamentos proibidos, junto com emendar bounding boxes para raspar dados completos. Para um projeto acadêmico de demonstração, com poucos usuários e consultas moderadas, o uso é tolerado e legítimo. Mas fazer o backend chamar a Overpass a cada requisição de rota do usuário viola a política e, na prática, vai falhar por timeout na hora da apresentação.

LIMITES DO NOMINATIM: máximo absoluto de 1 req/s; proibido usar em autocomplete; cache local obrigatório; geocodificação em lote limitada a 4 req/min em thread única, sem paralelismo.

LIMITES DO OPENROUTESERVICE (plano gratuito): ~2.000 requisições/dia no endpoint de direções, 40 por minuto em janela deslizante, cotas cumulativas entre endpoints. Perfil wheelchair limitado a 300 km por rota (irrelevante para uso urbano).

LIMITES DOS TILES: cache mínimo de 7 dias, proibido pre-seeding e uso offline, "o acesso pode ser retirado a qualquer momento".

TERMOS DE USO / LICENÇA: dados sob ODbL (Open Database License). Uso gratuito inclusive comercial, desde que haja atribuição e que bancos derivados sejam compartilhados sob a mesma licença.

CUSTO DA ALTERNATIVA LOCAL: 857 MB de download único (extrato Sudeste), mais espaço em disco para o PostGIS. Se o extrato for recortado só para a bbox de SP e filtrado por tags de acessibilidade com osmium, o banco final cabe tranquilamente em qualquer notebook ou em tiers gratuitos de nuvem.

## Riscos
- COBERTURA INSUFICIENTE PARA ROTEAMENTO CONFIÁVEL — é o maior risco técnico e ele é mensurável: apenas 1,9% das travessias de SP têm kerb=*, só 5% das escadas informam ramp=*, e smoothness existe em 51 vias na cidade inteira. Uma rota calculada só com dados OSM pode mandar um cadeirante por um caminho que o mapa não sabe que tem degrau. Nunca apresente as rotas como garantidas; rotule-as como sugestões baseadas em dados colaborativos incompletos.
- DEPENDER DA OVERPASS EM TEMPO DE EXECUÇÃO — a política proíbe usá-la como backend de produção, e nos meus testes as três instâncias públicas falharam repetidamente por sobrecarga. Se a demonstração para a banca depender de uma chamada ao vivo à Overpass, há chance concreta de o sistema travar na frente do professor.
- ESPELHO DESATUALIZADO SEM AVISO — o kumi.systems, que é o espelho mais recomendado por ser rápido e sem limite de slots, estava com dados de 01/06/2026, três meses defasados, e nada na resposta alerta sobre isso além do campo timestamp_osm_base. O grupo pode passar semanas trabalhando com dados velhos sem perceber.
- DOIS ESQUEMAS DE CALÇADA CONVIVENDO EM SP — 4.703 calçadas como geometria própria (footway=sidewalk) contra 10.088 vias com o atributo sidewalk=*. A comunidade brasileira não tem padrão consolidado e São Paulo tem esquemas sobrepostos sem coordenação. Um roteador que só entenda um dos esquemas vai gerar rotas desconexas ou ignorar metade da cidade.
- CONFUNDIR wheelchair=no DE POI COM BARREIRA DE CALÇADA — dos 1.833 objetos wheelchair=no em SP, a maioria são estabelecimentos (lojas, restaurantes) cujo acesso interno tem degrau, não obstáculos no percurso. Notei isso ao inspecionar a resposta do benchmark: os resultados vinham cheios de tags addr:street e addr:housenumber. Tratar POI inacessível como barreira de rota vai poluir o grafo com falsos positivos.
- SHARE-ALIKE DO ODbL — se o projeto publicar um banco derivado (extração substancial do OSM combinada com as barreiras cadastradas pelos usuários), o ODbL obriga a licenciar esse banco em ODbL. Isso é perfeitamente aceitável num trabalho acadêmico, mas precisa estar documentado no relatório e no repositório para não virar problema de conformidade na avaliação.
- ESQUECER A ATRIBUIÇÃO — omitir '© OpenStreetMap contributors' com link para openstreetmap.org/copyright viola a licença. É a falha mais fácil de cometer e a mais fácil de evitar; num projeto cujo tema é justamente inclusão e conformidade, seria contraditório.
- NOMINATIM EM AUTOCOMPLETE — a política proíbe explicitamente. Uma caixa de busca de endereço em React que dispare a cada tecla vai gerar dezenas de requisições por segundo, muito acima do limite de 1 req/s, e resultará em bloqueio do IP. Risco alto porque é o padrão natural de implementação.
- CORTE DO ACESSO AOS TILES — a política avisa que o acesso a tile.openstreetmap.org pode ser retirado a qualquer momento sem aviso, especialmente se o User-Agent for genérico. O mapa simplesmente para de carregar.
- DEPENDÊNCIA DA CHAVE DO OPENROUTESERVICE — se o grupo adotar o ORS como motor de rotas, as 2.000 requisições/dia são compartilhadas entre todos os desenvolvedores testando. Em dia de integração ou de apresentação, a cota pode estourar. Vale ter chaves separadas por integrante e cache das rotas mais consultadas.
- WHEELMAP COMO FONTE COMPLEMENTAR É POUCO VIÁVEL — a API clássica está desligada (conexão recusada) e a sucessora exige token organizacional via wheelmap.pro. Além disso, como o Wheelmap sincroniza com o OSM, o ganho de dados sobre consultar wheelchair=* diretamente seria pequeno. Não vale gastar tempo do cronograma tentando obter o acesso.
- VANDALISMO E QUALIDADE NOS DADOS COLABORATIVOS PRÓPRIOS — o sistema aceita cadastro de barreiras pelos usuários. Sem moderação, votação de confirmação ou expiração de reportes antigos, uma barreira temporária (obra que acabou) pode bloquear uma rota para sempre. Isso é requisito de produto, não detalhe técnico.
- VIÉS GEOGRÁFICO DA COBERTURA — o mapeamento sistemático de acessibilidade em SP se concentrou na Lapa e na Vila Mariana (projeto SMPED/SMT de 2021). A qualidade dos dados é muito melhor nesses bairros do que na periferia, justamente onde as barreiras são piores. Se a demonstração usar só a região central, ela superestima a capacidade real do sistema.

## Recomendações para o projeto
- NÃO chame a Overpass em tempo de execução. Adote a arquitetura de pré-processamento: baixe o extrato Geofabrik do Sudeste (857 MB), recorte a bbox de São Paulo com osmium extract, filtre as tags de acessibilidade com osmium tags-filter, carregue no PostgreSQL/PostGIS e sirva tudo a partir do seu próprio banco. Isso resolve de uma vez a proibição da política, os 12 segundos de latência e a instabilidade que encontrei nos testes.
- Use a Overpass apenas como ferramenta de desenvolvimento e para atualizações periódicas (ex.: um job semanal que traz o que mudou), nunca no caminho da requisição do usuário. Nesse uso, ela é perfeitamente legítima e dentro da política.
- Sempre verifique o campo timestamp_osm_base da resposta Overpass antes de confiar num espelho. Prefira overpass-api.de para dados atuais; use kumi.systems só para consultas exploratórias pesadas, ciente de que os dados podem estar meses atrasados.
- Adote o OpenRouteService com o perfil wheelchair como motor de rotas em vez de implementar roteamento do zero. Ele já modela maximum_incline, maximum_sloped_kerb e minimum_width — exatamente as variáveis do problema. Isso economiza semanas de cronograma e permite ao grupo focar no diferencial real do projeto, que é a camada colaborativa de barreiras.
- Modele as barreiras cadastradas pelos usuários como uma camada de penalização no grafo, e não como dado que sobrescreve o OSM. Na prática: cada barreira reportada adiciona custo às arestas próximas, e a rota final é o caminho de menor custo combinado. Isso mantém a distinção clara entre dado oficial e dado colaborativo.
- Priorize as tags que realmente têm cobertura em SP. Por ordem de aproveitamento imediato: highway=steps (3.652 escadas — o dado mais confiável e visualmente impactante), kerb=raised/lowered (6.174 nós), tactile_paving (5.214), incline (902). Trate smoothness como inexistente (51 ocorrências) e não construa nenhuma funcionalidade que dependa dela.
- Separe semanticamente wheelchair=* em POI de barreira no percurso. Um wheelchair=no numa loja é informação de destino; um degrau na calçada é obstáculo de rota. Use highway/footway como discriminador e nunca misture os dois no cálculo do caminho.
- Suporte os DOIS esquemas de calçada desde o início: footway=sidewalk como geometria própria E sidewalk=* como atributo da via. Em São Paulo os dois coexistem, e ignorar um deles deixa buracos na rede em bairros inteiros.
- Coloque a atribuição '© OpenStreetMap contributors' com link para openstreetmap.org/copyright de forma permanentemente visível no mapa. Como o público-alvo depende de acessibilidade, garanta que a atribuição também seja acessível a leitores de tela (não a esconda em elemento puramente visual) — isso vira ponto positivo na avaliação de WCAG/eMAG.
- Na caixa de busca de endereço, NUNCA chame o Nominatim a cada tecla. Use debounce de pelo menos 1 segundo e dispare só no submit, ou melhor: pré-carregue os logradouros de SP no seu próprio PostGIS a partir do extrato OSM e faça o autocomplete localmente. Além de cumprir a política, fica instantâneo.
- Faça a demonstração com dados pré-carregados e cacheados, jamais dependendo de chamada externa ao vivo. Considere focar a demo na Lapa ou Vila Mariana, onde o mapeamento sistemático do projeto SMPED/SMT deixou a melhor cobertura — mas seja honesto no relatório sobre o viés geográfico dessa escolha.
- Cite o projeto 'Calçadas Urbanas Inclusivas' (SMPED, SMT, G3ict, Universidade de Washington, Microsoft) na fundamentação teórica. É um precedente municipal oficial que legitima academicamente a proposta e demonstra pesquisa de contexto local.
- Inclua as estatísticas de cobertura deste relatório na justificativa do trabalho. O fato de apenas 1,9% das travessias de SP terem informação de guia rebaixada é o argumento mais forte possível para a existência do sistema colaborativo que vocês estão propondo — transforma uma limitação em fundamentação.
- Descarte o Wheelmap/accessibility.cloud do escopo. A API clássica está desligada, a nova exige cadastro organizacional e o ganho sobre o OSM direto é marginal, já que as bases sincronizam. Mencione a avaliação no relatório como decisão técnica justificada, mas não gaste cronograma tentando integrar.
- Preveja moderação dos reportes colaborativos: confirmação por outros usuários, expiração automática de barreiras antigas e possibilidade de marcar 'resolvido'. Sem isso, a base degrada rapidamente e obras temporárias viram bloqueios permanentes.
- Tenha um plano B para os tiles (MapTiler ou Stadia Maps têm planos gratuitos), já que a política do OSM permite corte de acesso sem aviso. Configure um User-Agent próprio identificando a aplicação desde o primeiro dia.

## Implicações para a escolha de backend
Este tema é o argumento mais forte a favor do Python, e por razões técnicas concretas, não apenas por facilidade de aprendizado.

PYTHON (recomendado). O ecossistema geoespacial e de OSM em Python não tem equivalente em maturidade nas outras duas linguagens. Para o pipeline exato que este projeto precisa existe uma ferramenta pronta e bem documentada em cada etapa: pyosmium e osmium-tool para recortar e filtrar o PBF; pyrosm para ler o .osm.pbf direto para GeoDataFrames (cerca de 12x mais rápido que o OSMnx no benchmark oficial, porque é escrito em Cython e lê o dump local em vez de ir à rede); OSMnx para montar o grafo da rede pedonal já topologicamente correto; NetworkX para o caminho mínimo com pesos personalizados (que é onde entram as barreiras colaborativas); GeoPandas e Shapely para geometria; e GeoAlchemy2 ou GeoDjango para persistir em PostGIS. Com FastAPI, o backend expõe isso ao React com tipagem via Pydantic e documentação OpenAPI automática, que casa bem com o TypeScript do frontend. Um detalhe que costuma passar despercebido: a Overpass API só devolve texto e JSON, então quase todo o trabalho real é transformar dados geoespaciais — exatamente o que o Python faz melhor. Além disso, praticamente todos os tutoriais, notebooks e artigos acadêmicos de mapeamento de acessibilidade com OSM estão em Python, o que reduz muito o custo de pesquisa para uma equipe pequena e com prazo de um semestre.

JAVA. Tem um trunfo específico e relevante: o GraphHopper, motor de roteamento maduro escrito em Java, que pode ser embarcado como biblioteca e permite perfis customizados por expressão. Se o grupo quisesse construir o próprio motor de rotas em vez de usar o OpenRouteService, Java seria a escolha mais sólida — e vale notar que o próprio OpenRouteService é construído sobre o GraphHopper. Para leitura de PBF existem Osmosis e osm4j. Porém, o processamento geoespacial exploratório (a parte de investigar tags, medir cobertura, limpar dados) é sensivelmente mais verboso, e a equipe gastaria tempo com infraestrutura em vez de com o problema de acessibilidade. Só compensa se alguém do grupo já dominar Java e o escopo incluir roteamento próprio.

C#. É a opção mais fraca para este tema específico. Existe o OsmSharp para ler PBF e o Itinero para roteamento, mas ambos têm comunidade pequena, documentação escassa e histórico de manutenção irregular. Não há equivalente ao pyrosm ou ao OSMnx. O NetTopologySuite cobre geometria e o Npgsql funciona bem com PostGIS, então é viável — mas o grupo estaria constantemente reimplementando o que em Python é uma linha. Só se justificaria por familiaridade prévia forte da equipe com .NET.

VEREDITO PRÁTICO. Escolher Python aqui não é abrir mão de rigor técnico para ganhar facilidade: é a escolha tecnicamente correta para um projeto cujo núcleo é processar dados OSM e calcular rotas com pesos customizados. A arquitetura recomendada é FastAPI + PostgreSQL/PostGIS, com ETL do extrato Geofabrik via osmium e pyrosm, OpenRouteService (perfil wheelchair) como motor de rotas, e as barreiras colaborativas em tabela própria aplicadas como camada de penalização sobre o grafo. Isso alinha a preferência do usuário com a decisão técnica defensável — e sobra cronograma para o que de fato será avaliado com rigor, que é a acessibilidade WCAG/eMAG do próprio site.
