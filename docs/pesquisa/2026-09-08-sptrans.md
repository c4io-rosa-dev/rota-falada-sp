# Pesquisa: API SPTrans Olho Vivo e dados de transporte público de São Paulo (ônibus, Metrô, CPTM, concessionárias) para o Guia de Rotas de Transporte com Alertas de Barreiras Físicas

## Resumo original
A API Olho Vivo da SPTrans é gratuita, está no ar (verificado por requisição real em 2026-09-08) e é a única fonte oficial de tempo real para os ônibus de São Paulo. O acesso exige cadastro no portal de desenvolvedores da SPTrans, criação de um "aplicativo" em "Meus Aplicativos" e uso de um token em POST /Login/Autenticar, que devolve um cookie de sessão apiCredentials que precisa ser reenviado em todas as chamadas seguintes. Testei os cabeçalhos da API diretamente com curl e ela NÃO devolve nenhum header Access-Control-Allow-Origin, nem em requisições simples nem em preflight OPTIONS: portanto é tecnicamente impossível chamar o Olho Vivo direto do React no navegador, e um backend proxy é obrigatório, não opcional. Existe sim um campo de acessibilidade: no endpoint /Posicao, dentro do array vs, o campo "a" é um booleano documentado como "Indica se o veículo é acessível para pessoas com deficiência", mas ele descreve o VEÍCULO (elevador/rampa no ônibus), não a calçada, o ponto de parada nem a rota — ou seja, resolve só a última perna do problema do projeto, e as barreiras físicas de calçada continuam dependendo do OpenStreetMap e do cadastro colaborativo dos usuários. O GTFS estático da SPTrans está muito atualizado (versão de 2026-09-08 registrada no Transitland) e baixa por uma URL que exige login de desenvolvedor, mas contém apenas as seis tabelas obrigatórias mais shapes.txt e frequencies.txt, sem pathways.txt/levels.txt e sem campos de acessibilidade preenchidos de forma confiável. Não existe feed GTFS-realtime público para São Paulo. Para trilhos, a antiga fonte agregada mudou: a API Trilhos da ARTESP passou a exigir chave desde 25/06/2026, limita a 12 requisições por hora e, desde 03/09/2026, cobre apenas concessionárias (ViaQuatro, ViaMobilidade) — Metrô e CPTM ficaram de fora. Não existe, em nenhuma fonte oficial, API ou feed de status de elevadores e escadas rolantes: o Metrô publica a relação de elevadores apenas como PDF estático. Para uma equipe pequena com orçamento zero, isso empurra o projeto para tratar Olho Vivo como um enriquecimento opcional (mostrar se o ônibus que vem é acessível) e não como o núcleo do roteamento.

## Resumo corrigido pelo verificador (confiabilidade 6.5/10)
A API Olho Vivo da SPTrans é gratuita, está no ar e é a única fonte oficial de tempo real dos ônibus de São Paulo; tudo o que o relatório afirmou sobre ela foi confirmado por requisição real em 2026-09-08. A ausência total de CORS é verdadeira e verifiquei pessoalmente: nem GET, nem POST, nem preflight OPTIONS devolvem Access-Control-Allow-Origin, então o backend proxy é obrigatório e a ideia de um app só de frontend está descartada. Também confirmei as três pegadinhas de implementação: POST /Login/Autenticar sem Content-Length devolve HTTP 411, com Content-Length 0 e token inválido devolve HTTP 200 com corpo literal 'false', e qualquer chamada sem sessão devolve HTTP 401 com {"Message":"Authorization has been denied for this request."}, que é o gatilho de reautenticação. O campo 'a' de /Posicao existe e é acessibilidade do veículo, px é longitude e py é latitude, e 'a' significa área de operação em /Empresa — todas as armadilhas apontadas procedem. Onde o relatório errou feio foi no GTFS: baixei o feed sem nenhum login e recebi HTTP 200 com 14 MB, de modo que o download é anônimo e perfeitamente automatizável em CI, ao contrário do que ele afirmou com confiança alta. O feed de 2026-09-08 tem 10 tabelas e não 8, incluindo fare_attributes.txt e fare_rules.txt, e não tem duplicatas nem em agency.txt (uma linha só) nem em calendar.txt (seis service_id distintos) — essa alegação de duplicatas não só é falsa como contradiz a própria fonte que ele citou, um capítulo do IPEA que descreve o feed de 2019. Em compensação, a hipótese que o relatório marcava como provável agora é certeza: stops.txt não tem wheelchair_boarding, trips.txt não tem wheelchair_accessible, e não existem pathways.txt nem levels.txt, então o GTFS não contribui em nada para acessibilidade. Descobri dois problemas que ele não viu: route_id é idêntico a route_short_name, e não existe calendar_dates.txt, ou seja, feriados simplesmente não são modelados. O segundo erro grave foi sobre o Direto dos Trens: ele existe como API oficial, gratuita em regime best-effort, documentada em Swagger, com token pedido por e-mail e uso acadêmico explicitamente encorajado — o relatório concluiu que não havia API porque /api devolve 404, quando /api/status devolve 401 apontando a documentação. Como a ARTESP de fato excluiu Metrô e CPTM desde 03/09/2026 (isso está correto, assim como a chave obrigatória desde 25/06/2026 e o limite de 12 requisições por hora), o Direto dos Trens passou a ser a melhor fonte autorizada de status de Metrô e CPTM para este projeto, e recusá-la por medo de scraping antiético é rejeitar exatamente o caminho legítimo. Continua verdadeiro que não existe nenhuma fonte de status de elevador ou escada rolante: a página do Metrô é só um redirect para um PDF de maio de 2023, e transformar esse vazio em funcionalidade colaborativa segue sendo a melhor decisão de produto do relatório. A maior omissão, porém, é o GeoSampa: a Prefeitura publica de graça uma camada de calçadas com área, largura e declividade de cerca de 65 milhões de m², além de uma camada de acessibilidade e do traçado do Plano Emergencial de Calçadas — dado oficial e georreferenciado sobre o problema central do projeto, que deveria ser a primeira fonte investigada e não foi sequer mencionada. Por fim, a recomendação de Python com FastAPI permanece correta, mas o argumento de que não existe nada em Python está errado, porque há o pacote olhovivo no PyPI de outubro de 2024; o motivo real para escolher Python é o ecossistema geoespacial e de GTFS, não a ausência de alternativas.

  - Motivo: REFUTADO EMPIRICAMENTE. Baixei a URL em 2026-09-08 sem nenhum cookie, token ou login e recebi HTTP 200 com application/octet-stream de 14.288.302 bytes (zip GTFS válido, arquivos datados de 2026-09-08 11:19). Não há redirect para tela de login nem 401/403. O relatório derivou desse erro dois riscos e uma recomendação inteiros ('impede automação simples de atualização', 'cria dependência de um passo manual', 'trate como seed manual'), que caem junto.
  - Correção: O download do GTFS da SPTrans é ANÔNIMO e automatizável. `curl -L -o gtfs.zip http://www.sptrans.com.br/umbraco/Surface/PerfilDesenvolvedor/BaixarGTFS` funciona em CI/cron sem credencial. A equipe pode agendar atualização automática do feed; só é prudente cachear e checar o tamanho/data, porque o feed é atualizado quase diariamente.
  - Fonte: Teste próprio com curl em 2026-09-08 22:1x UTC contra http://www.sptrans.com.br/umbraco/Surface/PerfilDesenvolvedor/BaixarGTFS (HTTP 200, 14.288.302 bytes, sem autenticação)

Zero duplicatas. ## Lacunas apontadas
- LACUNA MAIS GRAVE — GEOSAMPA. O relatório afirma que o núcleo do projeto 'tem que ser construído sobre OpenStreetMap + cadastro colaborativo' e nunca menciona o GeoSampa, que é a fonte oficial e gratuita da Prefeitura de São Paulo com uma camada 'Calçadas' cobrindo cerca de 65 milhões de m² de passeio, com ÁREA, LARGURA e DECLIVIDADE de cada calçada — exatamente as variáveis que determinam se um cadeirante passa. Há também uma camada 'Acessibilidade' e o traçado do Plano Emergencial de Calçadas (PEC). Tudo baixável em shapefile/KMZ/DXF. Isso é dado oficial, georreferenciado, de graça, sobre o problema CENTRAL do projeto — e ficou de fora de um relatório que dedicou parágrafos a um campo booleano de acessibilidade de ônibus. Deveria ser a primeira fonte investigada.
- Ausência de calendar_dates.txt no GTFS não foi detectada nem discutida. Sem essa tabela não existe modelagem de feriado: o sistema vai calcular horários de dia útil em feriados. Para um público que depende de planejamento prévio de deslocamento, errar o dia de operação é uma falha funcional séria.
- Não trata da chave de junção entre o GTFS e a API Olho Vivo. O stop_id do GTFS (ex.: 18848) e o codigoParada (cp) da API (ex.: 340015329) são espaços de identificadores diferentes, assim como route_id ('1012-10') e codigoLinha (cl, numérico). O relatório recomenda usar o GTFS como seed e o Olho Vivo para tempo real sem dizer como amarrar os dois — que é justamente a parte difícil da integração.
- Armadilha de fuso horário não mencionada: o campo 'ta' é timestamp UTC em ISO 8601, enquanto 'hr' e 't' vêm em horário local de São Paulo. Misturar os dois produz previsões com 3 horas de erro — bug clássico e silencioso.
- Não menciona o /Posicao/Garagem nem o problema dos veículos transmitindo de dentro da garagem, que aparecem em /Posicao e sujam o mapa com ônibus fora de operação.
- Não menciona a EMTU nem os ônibus metropolitanos. A SPTrans cobre só o município; quem mora na Grande São Paulo e usa linhas intermunicipais fica sem cobertura. Existe GTFS da EMTU publicamente disponível. Se o escopo do projeto é 'a cidade de São Paulo', vale declarar isso explicitamente como limite; se não é, falta uma fonte inteira.
- Não aborda como exibir dados de tempo real de forma acessível — que é obrigação do projeto, não detalhe. Previsões que mudam sozinhas na tela precisam de aria-live com polidez adequada, de anúncio controlado para leitor de tela e de não roubar foco. Um painel de 'próximo ônibus' mal implementado é exatamente o tipo de coisa que quebra WCAG num projeto cujo público-alvo depende de tecnologia assistiva.
- Não sugere a Lei de Acesso à Informação / e-SIC como caminho para obter dados de elevadores do Metrô e da CPTM. Para um trabalho acadêmico, protocolar um pedido de acesso à informação é gratuito, legítimo, tem prazo legal de resposta e rende ótimo material de relatório — bem melhor do que declarar a lacuna e parar.
- Não discute o que o roteamento a pé acessível exige na prática. Sem pathways.txt, nenhum motor GTFS resolve o trecho intra-estação; o roteamento pedestre teria que sair de OSM com OSRM/Valhalla/OTP2 e perfil customizado, ponderando declividade e largura (que o GeoSampa fornece). O relatório recomenda 'construir sobre OSM' sem dizer com qual ferramenta, o que deixa o item mais caro do projeto sem estimativa.
- Não mediu nem estimou o tamanho real e a frequência de atualização das respostas de /Posicao e /Previsao/Parada, apesar de recomendar cache de 20-30s. Sem número, a recomendação de cache é chute — e o dimensionamento importa numa hospedagem gratuita.
- Não avalia a qualidade e a cobertura das tags de acessibilidade do OSM em São Paulo (wheelchair=*, kerb=*, sidewalk=*, incline). O relatório empurra o núcleo do projeto para o OSM sem verificar se o OSM de SP tem densidade de dados suficiente para isso — é a mesma falta de ceticismo que ele corretamente aplicou ao campo 'a' da SPTrans.
- Não menciona que a API Trilhos da ARTESP também exige allowlist de IP (403), o que na prática inviabiliza hospedagem gratuita com IP dinâmico — o relatório cita o 403 mas não conclui que isso, somado ao orçamento zero, provavelmente elimina a ARTESP do projeto por razão de infraestrutura, e não só de escopo.

## Fatos levantados
- [alta] A URL base da API é https://api.olhovivo.sptrans.com.br/v2.1 e o uso de HTTPS passou a ser obrigatório: o acesso via HTTP foi desativado após 02/01/2024. (fonte: https://www.sptrans.com.br/desenvolvedores/api-do-olho-vivo-guia-de-referencia/documentacao-api/)
- [alta] Para obter o token é preciso criar conta na área de desenvolvedores da SPTrans (https://www.sptrans.com.br/desenvolvedores/cadastro-desenvolvedores/); após a validação do cadastro, cada aplicativo registrado em 'Meus Aplicativos' recebe uma chave de acesso própria. (fonte: https://www.sptrans.com.br/desenvolvedores/ e https://www.sptrans.com.br/desenvolvedores/api-do-olho-vivo-guia-de-referencia/)
- [alta] A autenticação é feita por POST em /Login/Autenticar?token=SUA_CHAVE e retorna literalmente true ou false no corpo. A resposta traz um header Set-Cookie com apiCredentials=... que deve ser extraído e reenviado como header Cookie em todas as requisições seguintes; sem isso a API não responde corretamente. (fonte: https://www.sptrans.com.br/desenvolvedores/api-do-olho-vivo-guia-de-referencia/documentacao-api/ e https://forum.processing.org/two/discussion/22588/http-requests-cookies-sptrans-olho-vivo.html)
- [alta] VERIFICADO EM 2026-09-08 POR REQUISIÇÃO REAL: POST https://api.olhovivo.sptrans.com.br/v2.1/Login/Autenticar?token=INVALIDO retornou HTTP 200 com corpo 'false'. A API roda em ASP.NET (header X-AspNet-Version: 4.0.30319) atrás da Cloudflare. (fonte: Teste próprio com curl contra api.olhovivo.sptrans.com.br em 2026-09-08 22:00 UTC)
- [alta] VERIFICADO EM 2026-09-08: a API NÃO envia nenhum header Access-Control-Allow-Origin. Enviei Origin: https://example.com em POST, em GET e em preflight OPTIONS — nenhuma das três respostas trouxe qualquer header CORS. O OPTIONS respondeu 200 apenas com Allow/Public. Consequência: o navegador bloqueia qualquer fetch direto do React, e chamar a API do frontend é IMPOSSÍVEL. Um backend proxy é obrigatório. (fonte: Teste próprio com curl (-X OPTIONS e -X GET com header Origin) em 2026-09-08)
- [alta] VERIFICADO EM 2026-09-08: um POST em /Login/Autenticar sem corpo e sem Content-Length retorna HTTP 411 Length Required. É preciso mandar Content-Length: 0 (ou um corpo vazio explícito). Essa é uma pegadinha real de implementação que quebra clientes ingênuos. (fonte: Teste próprio com curl em 2026-09-08)
- [alta] VERIFICADO EM 2026-09-08: uma chamada GET a /Posicao sem sessão autenticada retorna HTTP 401 com o corpo {"Message":"Authorization has been denied for this request."} — esse é o sinal para o backend reautenticar e refazer a requisição. (fonte: Teste próprio com curl em 2026-09-08)
- [alta] O CAMPO DE ACESSIBILIDADE EXISTE E É O CAMPO 'a': no endpoint /Posicao, dentro do array vs (veículos), o campo 'a' é do tipo bool e está documentado literalmente como 'Indica se o veículo é acessível para pessoas com deficiência'. Ele aparece também em /Posicao/Linha e nos veículos retornados pelos endpoints de Previsão. (fonte: https://www.sptrans.com.br/desenvolvedores/api-do-olho-vivo-guia-de-referencia/documentacao-api/)
- [alta] O campo 'a' descreve o VEÍCULO (piso baixo / elevador / rampa embarcada), não o ponto de parada, não a calçada e não o itinerário. Ele não diz nada sobre a existência de rampa no meio-fio, sobre o estado do passeio nem sobre a acessibilidade do terminal — ou seja, não substitui o cadastro colaborativo de barreiras que é o núcleo do projeto. ## Endpoints / recursos
- **Autenticação Olho Vivo** — POST https://api.olhovivo.sptrans.com.br/v2.1/Login/Autenticar?token={SUA_CHAVE}
  - Retorna: Corpo literal true ou false (HTTP 200 nos dois casos). O header Set-Cookie traz apiCredentials=... que deve ser reenviado como Cookie em todas as chamadas seguintes. ATENÇÃO: exige Content-Length: 0, senão retorna HTTP 411.
  - Exemplo: `curl -i -X POST 'https://api.olhovivo.sptrans.com.br/v2.1/Login/Autenticar?token=SEU_TOKEN' -H 'Content-Length: 0' -c cookies.txt`
- **Posicao (POSIÇÃO DE TODOS OS VEÍCULOS — contém o campo de acessibilidade)** — GET /v2.1/Posicao (sem parâmetros), com header Cookie: apiCredentials=...
  - Retorna: { hr: horário de referência, l: [ { c: letreiro completo, cl: código da linha, sl: sentido (1|2), lt0: letreiro destino, lt1: letreiro origem, qv: qtd veículos, vs: [ { p: prefixo do veículo, a: BOOL — 'Indica se o veículo é acessível para pessoas com deficiência', ta: timestamp UTC ISO 8601 da captura, py: latitude, px: longitude } ] } ] }. É a resposta MAIS PESADA da API (frota inteira da cidade) — prefira /Posicao/Linha.
  - Exemplo: `curl 'https://api.olhovivo.sptrans.com.br/v2.1/Posicao' -b cookies.txt`
- **Posicao/Linha (posição dos veículos de UMA linha)** — GET /v2.1/Posicao/Linha?codigoLinha={cl}
  - Retorna: Mesma estrutura de /Posicao, restrita a uma linha. Inclui o campo a (acessibilidade do veículo). É esta a chamada que o projeto deve usar, não a /Posicao completa.
  - Exemplo: `curl 'https://api.olhovivo.sptrans.com.br/v2.1/Posicao/Linha?codigoLinha=1273' -b cookies.txt`
- **Linha/Buscar** — GET /v2.1/Linha/Buscar?termosBusca={texto ou número, total ou parcial}
  - Retorna: Array de linhas: cl (código único POR SENTIDO — cuidado: a mesma linha tem dois cl), lc (bool, opera em modo circular), lt (primeira parte do letreiro numérico), tl (segunda parte do letreiro), sl (sentido: 1 = Principal→Secundário, 2 = Secundário→Principal), tp (letreiro descritivo no sentido principal), ts (letreiro descritivo no sentido secundário).
  - Exemplo: `curl 'https://api.olhovivo.sptrans.com.br/v2.1/Linha/Buscar?termosBusca=8000' -b cookies.txt`
- **Linha/BuscarLinhaSentido** — GET /v2.1/Linha/BuscarLinhaSentido?termosBusca={texto}&sentido={1|2}
  - Retorna: A mesma estrutura de Linha/Buscar, filtrada por um único sentido de operação.
  - Exemplo: `curl 'https://api.olhovivo.sptrans.com.br/v2.1/Linha/BuscarLinhaSentido?termosBusca=8000&sentido=1' -b cookies.txt`
- **Parada/Buscar (pontos de parada georreferenciados)** — GET /v2.1/Parada/Buscar?termosBusca={nome da parada ou endereço}
  - Retorna: Array de paradas: cp (código da parada), np (nome da parada), ed (endereço de localização), py (LATITUDE), px (LONGITUDE). Observação importante: px/py são invertidos em relação à convenção usual — px é longitude e py é latitude. NÃO há nenhum campo de acessibilidade da parada.
  - Exemplo: `curl 'https://api.olhovivo.sptrans.com.br/v2.1/Parada/Buscar?termosBusca=Av.%20Paulista' -b cookies.txt`
- **Parada/BuscarParadasPorLinha** — GET /v2.1/Parada/BuscarParadasPorLinha?codigoLinha={cl}
  - Retorna: Todas as paradas atendidas por uma linha, com cp/np/ed/py/px. Útil para desenhar o itinerário e cruzar cada parada com o cadastro colaborativo de barreiras do projeto.
  - Exemplo: `curl 'https://api.olhovivo.sptrans.com.br/v2.1/Parada/BuscarParadasPorLinha?codigoLinha=1273' -b cookies.txt`
- **Parada/BuscarParadasPorCorredor** — GET /v2.1/Parada/BuscarParadasPorCorredor?codigoCorredor={cc}
  - Retorna: Lista detalhada de todas as paradas que compõem um determinado corredor inteligente.
  - Exemplo: `curl 'https://api.olhovivo.sptrans.com.br/v2.1/Parada/BuscarParadasPorCorredor?codigoCorredor=8' -b cookies.txt`
- **Corredor** — GET /v2.1/Corredor (sem parâmetros)
  - Retorna: Array com cc (código único do corredor inteligente) e nc (nome do corredor). Corredores tendem a ter infraestrutura melhor (estações elevadas, plataformas niveladas) — pode ser um sinal heurístico de acessibilidade para o projeto.
  - Exemplo: `curl 'https://api.olhovivo.sptrans.com.br/v2.1/Corredor' -b cookies.txt`
- **Empresa** — GET /v2.1/Empresa (sem parâmetros)
  - Retorna: { hr: horário de referência, e: [ { a: CÓDIGO DA ÁREA DE OPERAÇÃO (int — cuidado: aqui 'a' NÃO é acessibilidade, é área!), c: código de referência da empresa, n: nome da empresa } ] }. Armadilha real: o campo 'a' tem significados totalmente diferentes em /Empresa (int, área) e em /Posicao (bool, acessibilidade).
  - Exemplo: `curl 'https://api.olhovivo.sptrans.com.br/v2.1/Empresa' -b cookies.txt`
- **Previsao (chegada em uma parada para uma linha)** — GET /v2.1/Previsao?codigoParada={cp}&codigoLinha={cl}
  - Retorna: { hr, p: { cp, np, py, px, l: [ { ...linha..., vs: [ { p: prefixo, t: HORÁRIO PREVISTO DE CHEGADA, a: acessibilidade do veículo, py, px } ] } ] } }. É aqui que o projeto consegue responder 'o próximo ônibus que chega neste ponto é acessível e chega às HH:MM'.
  - Exemplo: `curl 'https://api.olhovivo.sptrans.com.br/v2.1/Previsao?codigoParada=340015329&codigoLinha=1273' -b cookies.txt`
- **Previsao/Parada** — GET /v2.1/Previsao/Parada?codigoParada={cp}
  - Retorna: Previsões de TODAS as linhas que servem aquela parada. Provavelmente o endpoint mais útil do projeto: uma chamada devolve tudo que vai chegar naquele ponto, com o flag de acessibilidade por veículo.
  - Exemplo: `curl 'https://api.olhovivo.sptrans.com.br/v2.1/Previsao/Parada?codigoParada=340015329' -b cookies.txt`
- **Previsao/Linha** — GET /v2.1/Previsao/Linha?codigoLinha={cl}
  - Retorna: Previsões de chegada em todas as paradas atendidas pela linha. Resposta grande; usar com parcimônia.
  - Exemplo: `curl 'https://api.olhovivo.sptrans.com.br/v2.1/Previsao/Linha?codigoLinha=1273' -b cookies.txt`
- **KMZ (velocidade nas vias)** — GET /v2.1/KMZ, /KMZ/BC, /KMZ/CB, /KMZ/Corredor[/BC|/CB], /KMZ/OutrasVias[/BC|/CB]
  - Retorna: Mapa de velocidade das vias em formato KMZ (não JSON). BC = bairro→centro, CB = centro→bairro. Pouco relevante para acessibilidade; ignorar no escopo do projeto.
  - Exemplo: `curl 'https://api.olhovivo.sptrans.com.br/v2.1/KMZ' -b cookies.txt -o vias.kmz`
- **GTFS estático da SPTrans** — http://www.sptrans.com.br/umbraco/Surface/PerfilDesenvolvedor/BaixarGTFS — exige sessão autenticada de desenvolvedor no site da SPTrans (não é link anônimo)
  - Retorna: ZIP GTFS com as 6 tabelas obrigatórias (agency, stops, routes, trips, stop_times, calendar) + shapes.txt + frequencies.txt. Versão mais recente catalogada: 2026-09-08. Sem pathways.txt/levels.txt. Contém duplicatas conhecidas em agency.txt e calendar.txt.
  - Exemplo: `Baixar manualmente logado no portal, versionar o zip no repositório do projeto e carregar com gtfs-kit em Python`
- **Gateway APILIB da Prefeitura (alternativa ao endpoint direto)** — https://gateway.apilib.prefeitura.sp.gov.br/sptrans/olhovivo/v2.1 — exige cadastro e access token próprios do APILIB
  - Retorna: Mesma API Olho Vivo intermediada pelo gateway municipal. Pode servir de plano B se o endpoint direto instabilizar, mas adiciona um cadastro extra e também não publica SLA.
  - Exemplo: `https://apilib.prefeitura.sp.gov.br/store/apis/info?name=OlhoVivo&version=v2.1&provider=admin&tag=SPTrans`
- **API Trilhos da ARTESP (status metroferroviário — SÓ CONCESSIONÁRIAS)** — GET https://ccm.artesp.sp.gov.br/metroferroviario/api/status/ com header Authorization: Api-Key cci_metro_status_live_<id>_<random>
  - Retorna: JSON v1.1.0 com meta (versão, timestamp, filtros, contagens), empresas (id, nome, situação regulatória) e linhas (nome, código, ativa, classificação operacional, timestamp). Também há /ocorrencias/ (histórico até 365 dias) e /concessionarias/. Atualiza a cada 5 min. LIMITE: 12 req/hora. Desde 03/09/2026 NÃO cobre Metrô nem CPTM. SEM dados de elevador/escada rolante.
  - Exemplo: `curl -H 'Authorization: Api-Key SUA_CHAVE' 'https://ccm.artesp.sp.gov.br/metroferroviario/api/status/'`
- **metro-sp-api (não oficial, scraping)** — github.com/ale-jr/metro-sp-api — rodar localmente via Node.js 18+ ou Docker; GET http://localhost:5000
  - Retorna: { lines: [ { name, number, status: normal|reduced_speed|closed|paralyzed, statusDescription, reason, updatedAt } ] } cobrindo Metrô, CPTM, ViaQuatro e ViaMobilidade. Licença MIT. Parado desde ~2023 e sem instância pública — os seletores de scraping provavelmente já quebraram.
  - Exemplo: `docker run -p 5000:5000 metro-sp-api && curl http://localhost:5000`

## Limites e custos
CUSTO: zero. Tanto a API Olho Vivo quanto o GTFS da SPTrans são gratuitos — só exigem cadastro. Não há tier pago, não há cartão de crédito, não há cobrança por volume. Isso encaixa perfeitamente no orçamento zero do projeto.

CADASTRO E CHAVES (Olho Vivo): é preciso (1) criar conta em sptrans.com.br/desenvolvedores/cadastro-desenvolvedores/, (2) aguardar validação do cadastro, (3) entrar em "Meus Aplicativos" e registrar um aplicativo, que recebe a chave de acesso. Cada aplicativo tem sua própria chave — dá para gerar uma por integrante da equipe em desenvolvimento, o que é bom porque evita que todos compartilhem o mesmo token. A chave é um segredo: precisa ficar em variável de ambiente no backend, NUNCA no bundle do React.

RATE LIMITS (Olho Vivo): a SPTrans NÃO publica nenhum limite. Verifiquei as duas páginas oficiais de desenvolvedores e nenhuma menciona cota, throttling ou número máximo de chamadas. Isso é uma faca de dois gumes: não há limite documentado para respeitar, mas também não há garantia nenhuma de que não exista um limite não documentado que bloqueie a aplicação sem aviso. A postura segura é a equipe se autolimitar: cachear agressivamente no backend (paradas e linhas mudam raramente — cache de horas ou dias; posições e previsões mudam a cada ~30s, então cache de 20-30s já corta a esmagadora maioria das chamadas) e nunca fazer polling por usuário conectado.

SESSÃO: o cookie apiCredentials expira, mas a SPTrans não documenta em quanto tempo. O backend precisa tratar o HTTP 401 com corpo {"Message":"Authorization has been denied for this request."} como gatilho de reautenticação automática e retry — verifiquei esse comportamento na prática. Não implementar isso significa que a aplicação vai quebrar sozinha depois de algum tempo no ar.

TERMOS DE USO E LICENÇA: a SPTrans NÃO publica termos de uso, licença de dados nem exigência de atribuição em nenhuma das páginas de desenvolvedores. Para um trabalho acadêmico isso não é bloqueante, mas é boa prática (e boa nota) creditar "Dados: SPTrans / API Olho Vivo" na interface e na documentação, e registrar no relatório que a licença não é declarada publicamente.

RATE LIMIT DA API TRILHOS (ARTESP): este sim é severo e explícito — 12 requisições por hora por credencial, polling recomendado de no máximo 1 a cada 5 minutos, resposta 429 ao estourar, e headers X-RateLimit-Limit / X-RateLimit-Remaining / Retry-After. Também retorna 403 se o IP não estiver na allowlist, o que significa que hospedagem gratuita com IP dinâmico pode simplesmente não funcionar. Chave obrigatória desde 25/06/2026. 12 req/h é incompatível com chamada por usuário: obriga a um job agendado no backend que busca uma vez a cada 5 minutos e serve o resultado cacheado para todo mundo.

GTFS: download gratuito, mas exige login de desenvolvedor (não é URL anônima), o que impede baixar automaticamente em CI sem gerenciar sessão. O feed é grande (rede inteira de SP) e atualiza com frequência (mais de 100 versões catalogadas). Licença não declarada pela SPTrans.

## Riscos
- BLOQUEADOR TÉCNICO CONFIRMADO — CORS: testei a API com curl em 2026-09-08 e ela não devolve NENHUM header Access-Control-Allow-Origin, nem em GET, nem em POST, nem em preflight OPTIONS. O React não consegue chamar o Olho Vivo direto do navegador, ponto final. Isso não é contornável com configuração no frontend: exige um backend proxy. Se o grupo tinha planejado uma aplicação só de frontend, esse plano está morto.
- O campo de acessibilidade 'a' é do VEÍCULO, não do trajeto. O problema central do projeto — escadas, calçadas quebradas, falta de rampa no meio-fio — não é respondido por nenhum campo da API Olho Vivo. Existe um risco real de a equipe superestimar o valor da SPTrans e descobrir tarde que ela resolve só uma fatia pequena do escopo, com o roteamento acessível continuando totalmente dependente de OSM + cadastro colaborativo.
- O campo 'a' pode ter baixo poder discriminante: se quase toda a frota já é de piso baixo, filtrar por a=true não muda nada na prática e a funcionalidade vira enfeite. NÃO consegui confirmar a proporção real — a equipe precisa medir isso numa amostra de /Posicao antes de investir tempo na feature.
- Armadilha de nomenclatura: o campo 'a' significa coisas diferentes em endpoints diferentes. Em /Posicao é bool = acessibilidade do veículo; em /Empresa é int = código da área de operação. Tipar isso errado gera bug silencioso.
- Armadilha de coordenadas: px é LONGITUDE e py é LATITUDE — o oposto do que a intuição sugere (p de 'x' parecer latitude). Inverter isso joga todos os pontos no lugar errado do mapa, e é um erro clássico que só aparece visualmente.
- Armadilha do HTTP 411: um POST em /Login/Autenticar sem Content-Length falha com 411 Length Required em vez de dar erro de autenticação. Confirmei na prática. Um cliente ingênuo pode passar horas achando que o token está errado.
- Cada linha tem DOIS códigos cl (um por sentido). Tratar cl como identificador único da linha vai produzir itinerários incompletos ou duplicados.
- Ausência total de SLA, rate limit publicado e termos de uso da SPTrans: a API pode ficar instável, mudar de comportamento ou impor limites sem aviso, e não há canal formal de suporte nem compromisso de disponibilidade. Para um projeto com data de entrega fixa, isso significa que a demo pode falhar no dia da apresentação por motivo fora do controle da equipe.
- O cookie apiCredentials expira em tempo não documentado. Sem lógica de reautenticação no 401, a aplicação funciona nos testes e quebra sozinha depois de um tempo no ar — inclusive durante a apresentação.
- MUDANÇA REGULATÓRIA RECENTE (03/09/2026, cinco dias antes desta pesquisa): a API Trilhos da ARTESP deixou de cobrir Metrô e CPTM, restando só concessionárias. Qualquer tutorial, artigo ou código de exemplo anterior a essa data está desatualizado. Não existe mais uma fonte oficial única com status de todas as linhas de trilhos de SP.
- Rate limit de 12 req/hora da API Trilhos, somado ao possível bloqueio por IP não autorizado (403), pode inviabilizar o uso em hospedagem gratuita com IP dinâmico.
- NÃO EXISTE nenhuma fonte de dados de status de elevadores e escadas rolantes de Metrô/CPTM. O Metrô publica só um PDF estático de 2023. Como há casos documentados de elevadores parados por meses, o sistema não tem como avisar o cadeirante que o elevador da estação está quebrado — que é exatamente o tipo de barreira que o projeto se propõe a alertar. Essa lacuna precisa estar explícita no relatório como limitação conhecida.
- As alternativas para trilhos são todas frágeis: metro-sp-api faz scraping e está parado desde ~2023 (seletores provavelmente quebrados); Direto dos Trens não tem API pública documentada (o /api retornou 404) e usá-lo por scraping seria consumir um serviço de terceiros sem autorização, o que é eticamente questionável e tecnicamente instável.
- GTFS da SPTrans não tem pathways.txt nem levels.txt e provavelmente não tem wheelchair_boarding/wheelchair_accessible preenchidos — ou seja, o GTFS também não resolve acessibilidade. Além disso tem duplicatas conhecidas em agency.txt e calendar.txt que quebram parsers ingênuos.
- O download do GTFS exige login, o que impede automação simples de atualização e cria dependência de um passo manual.
- Não existe GTFS-realtime para São Paulo, então nenhuma biblioteca padrão de roteamento com tempo real (que espera GTFS-RT) funciona direto: seria preciso escrever um adaptador do formato proprietário do Olho Vivo.
- Ecossistema de bibliotecas fraco e envelhecido: os clientes Olho Vivo em Python são de 2013 e para a API v0 (obsoleta); em C# não existe nenhum publicado. O grupo vai escrever o cliente à mão de qualquer forma — o que é factível, mas precisa entrar na estimativa de esforço.

## Recomendações para o projeto
- TRATE O OLHO VIVO COMO ENRIQUECIMENTO, NÃO COMO NÚCLEO. O coração do projeto (rotas sem escadas, calçadas ruins, sem rampa) tem que ser construído sobre OpenStreetMap + o cadastro colaborativo dos próprios usuários. A SPTrans entra numa camada complementar: 'no ponto X, o próximo ônibus da linha Y chega às HH:MM e É acessível'. Escrever isso explicitamente no escopo evita que o grupo gaste tempo numa API que não responde a pergunta principal.
- CONSTRUA O BACKEND PROXY DESDE O PRIMEIRO SPRINT — não é opcional, é imposto pela ausência de CORS que confirmei empiricamente. O backend guarda o token em variável de ambiente, mantém a sessão (cookie apiCredentials), cacheia as respostas e expõe endpoints REST limpos e já normalizados para o React. Isso resolve CORS, segurança do token e rate limiting de uma vez só.
- IMPLEMENTE REAUTENTICAÇÃO AUTOMÁTICA NO 401. Encapsule todas as chamadas num wrapper que, ao receber HTTP 401 com {"Message":"Authorization has been denied for this request."}, refaz o POST /Login/Autenticar, atualiza o cookie e repete a requisição uma vez. Sem isso a aplicação quebra sozinha depois de um tempo no ar — inclusive na apresentação.
- LEMBRE DO Content-Length: 0 NO POST DE AUTENTICAÇÃO, senão vem HTTP 411 e não um erro de token. Em Python com requests, use requests.Session() e faça session.post(url) — a Session já gerencia o cookie apiCredentials sozinha, o que elimina toda a complexidade manual de cookie.
- CACHEIE POR TIPO DE DADO: /Parada/Buscar, /Linha/Buscar e /Corredor mudam raramente (cache de horas ou até dias, ou pré-carregue do GTFS); /Previsao e /Posicao mudam a cada ~30s (cache de 20-30s). Como não há rate limit publicado mas também nenhuma garantia, essa autodisciplina protege o projeto de um bloqueio surpresa.
- USE /Previsao/Parada COMO ENDPOINT PRINCIPAL: uma única chamada com o código da parada devolve todas as linhas que vão chegar ali, cada veículo com seu horário previsto (t) e seu flag de acessibilidade (a). É o melhor custo-benefício da API para o caso de uso do projeto. Evite /Posicao sem parâmetros (frota inteira da cidade, resposta enorme).
- MEÇA O CAMPO 'a' ANTES DE CONSTRUIR EM CIMA DELE. Logo na primeira sprint, faça uma chamada a /Posicao e calcule que porcentagem dos veículos tem a=true. Se for ~100%, o filtro 'só ônibus acessível' não agrega valor e o grupo deve realocar esse esforço para o cadastro colaborativo. Essa medição é barata e é uma decisão de produto baseada em evidência — ótimo material para o relatório.
- CUIDADO COM px/py: px é LONGITUDE, py é LATITUDE. Defina isso num tipo TypeScript explícito (ex.: { lat: number; lng: number }) na fronteira do backend, convertendo uma única vez, para que esse erro não se espalhe pelo código.
- NÃO CONFIE NO cl COMO ID DE LINHA: cada linha tem dois cl, um por sentido. Modele explicitamente linha + sentido no domínio da aplicação.
- BAIXE O GTFS UMA VEZ, VERSIONE O ZIP NO REPOSITÓRIO E CARREGUE NO BANCO. Como o download exige login e o feed é grande, trate-o como um seed de dados, não como uma integração ao vivo. Use o GTFS para popular paradas, linhas e itinerários (evitando milhares de chamadas à API) e deixe o Olho Vivo só para o tempo real. Lembre de deduplicar agency.txt e calendar.txt.
- ABRA O GTFS E CONFIRA wheelchair_boarding EM stops.txt E wheelchair_accessible EM trips.txt LOGO NO INÍCIO. É uma verificação de 10 minutos que decide se o GTFS contribui ou não para a acessibilidade. Minha expectativa é que estejam vazios ou ausentes — mas confirme, porque se estiverem preenchidos é um ganho grande de graça.
- ASSUMA A LACUNA DE ELEVADORES COMO LIMITAÇÃO DECLARADA E TRANSFORME-A EM FEATURE. Não existe API de status de elevador em SP. Em vez de tentar contornar com scraping frágil, deixe os PRÓPRIOS USUÁRIOS reportarem 'elevador da estação X quebrado' pelo mesmo fluxo colaborativo das barreiras de calçada. Isso é coerente com a proposta do projeto, é honesto no relatório, e vira um diferencial argumentativo forte: o sistema existe justamente porque o dado oficial não existe.
- EVITE A API TRILHOS DA ARTESP NO MVP. Ela mudou em 03/09/2026, exige chave, limita a 12 req/hora, pode bloquear por IP e — o mais decisivo — não cobre mais Metrô nem CPTM, que são as operadoras que mais importam para o público-alvo. Se for usar, faça um job agendado a cada 5 minutos servindo cache compartilhado, nunca chamada por usuário. Cite a mudança regulatória no relatório: é um achado atual e valorizado numa disciplina de Engenharia de Software.
- NÃO DEPENDA DE metro-sp-api NEM DE SCRAPING DO Direto dos Trens. O primeiro está parado desde ~2023 e o segundo não tem API pública documentada. Scraping de terceiro sem autorização é instável e eticamente frágil para um trabalho acadêmico.
- NÃO PROCURE MAIS UM CLIENTE PRONTO DE OLHO VIVO — escreva o seu. São 8 endpoints REST simples com um cookie de sessão; em Python isso é ~80 linhas com requests.Session. Os wrappers existentes ou são de outra linguagem, ou são para a v0 obsoleta. Escrever o próprio dá controle total sobre cache, retry e reautenticação, que é exatamente o que o projeto precisa.
- TENHA UM PLANO B PARA A APRESENTAÇÃO: como a API não tem SLA e pode cair, grave um snapshot real de respostas JSON (fixtures) e coloque uma flag no backend para servir dados mockados. Se a SPTrans estiver fora do ar no dia da entrega, a demo continua funcionando. Isso é gestão de risco concreta e rende pontos no relatório.

## Implicações para a escolha de backend
Este tema empurra a decisão claramente para PYTHON, e por razões objetivas, não só por o usuário achar Python mais fácil.

PRIMEIRO, A CONSTATAÇÃO QUE MUDA TUDO: não existe cliente Olho Vivo mantido em NENHUMA das três linguagens candidatas. Em Python o que há é um gist de 2013 e um pacote no readthedocs, ambos para a API v0 obsoleta (a atual é v2.1). Em Java há o tmoretto/java-olhovivo (wrapper Spring Boot para a v2.1) — nominalmente o melhor dos três, mas é um projeto comunitário pequeno sem garantia de manutenção. Em C#/.NET não encontrei absolutamente nada publicado no NuGet nem repositório de referência. Ou seja, a equipe vai escrever o cliente à mão em qualquer cenário, e o critério real passa a ser "em qual linguagem escrever esse cliente é mais barato" — e não "qual tem biblioteca pronta".

E aí Python ganha com folga. O padrão de autenticação do Olho Vivo é exatamente o caso de uso de requests.Session: você faz session.post('.../Login/Autenticar?token=...') uma vez e a Session passa a reenviar o cookie apiCredentials automaticamente em todas as chamadas seguintes, sem uma linha de gerenciamento manual de cookie. O cliente inteiro cabe em ~80 linhas. Em C# o equivalente exige montar HttpClient com HttpClientHandler + CookieContainer explícito; em Java, configurar CookieManager ou usar o wrapper de terceiro. Nenhum é difícil, mas Python é o único onde isso é praticamente de graça.

A DIFERENÇA DECISIVA, PORÉM, ESTÁ NO GTFS E NA GEOESPACIAL — que é onde o projeto realmente vive. Python tem gtfs-kit, pygtfs e make-gtfs mantidos no PyPI, além do ecossistema completo que o próprio IPEA usa nos estudos de acessibilidade urbana brasileira (r5py, OSMnx, geopandas, networkx). Isso importa muito aqui: o livro "Introdução à acessibilidade urbana" do IPEA — que foi justamente a fonte que me permitiu descobrir a composição real do GTFS da SPTrans — é escrito em R/Python e trata exatamente do problema de acessibilidade urbana no Brasil, com exemplos usando os dados de São Paulo. O grupo teria referência metodológica em português, com código, aplicada ao mesmo dado. Isso é um ativo enorme para um projeto acadêmico e não tem equivalente em C#.

Java é a alternativa séria e não deve ser descartada por preconceito: tem OpenTripPlanner, OneBusAway e GraphHopper, que são as ferramentas de referência mundial em roteamento multimodal com GTFS, e é a única das três com um wrapper Olho Vivo v2.1 existente. Se algum integrante já dominar Spring Boot, Java é defensável. A contrapartida é o custo de cerimônia: mais configuração, build mais pesado, iteração mais lenta — o que pesa negativamente numa equipe pequena de semestre curto.

C# é a opção mais fraca para ESTE projeto especificamente. Zero cliente Olho Vivo, ecossistema GTFS e geoespacial notavelmente mais pobre que o de Python e Java, e nenhuma vantagem compensatória no domínio de transporte público brasileiro. A ironia é que a própria API Olho Vivo roda em ASP.NET (confirmei pelo header X-AspNet-Version: 4.0.30319) — mas isso não gera nenhum benefício para quem a consome.

PONTO IMPORTANTE E TRANQUILIZADOR: a exigência do backend proxy, que a ausência de CORS torna obrigatória, é igualmente simples nas três linguagens. FastAPI, Spring Boot e ASP.NET Core resolvem isso trivialmente. Então o CORS não desempata a escolha — ele apenas confirma que ALGUM backend é obrigatório, o que aliás encerra qualquer discussão sobre fazer o projeto só com React.

RECOMENDAÇÃO: Python com FastAPI. Combina o cliente Olho Vivo mais barato de escrever, o melhor ecossistema GTFS e geoespacial, referência metodológica em português aplicada a dados de São Paulo, tipagem via Pydantic (que casa bem com o TypeScript do frontend e ajuda a evitar as armadilhas do campo 'a' polissêmico e do px/py invertido), e a menor curva para a equipe. Java fica como segunda opção legítima se houver experiência prévia forte com Spring; C# só se houver uma restrição externa da disciplina que obrigue.
